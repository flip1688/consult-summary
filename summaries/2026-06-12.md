### 3. Sports (Thunder Software) — Security / Scale / Optimize
- เอกสารทำมาด้วย AI (จากสรุปที่น้องทำ) มี 3 หัวข้อ: security, bottleneck, load — โดยรวมถือเป็นเรื่องเดียวกัน
- Stack ยังไม่เปลี่ยน แต่มีแผนอยากย้ายไป Kubernetes (ที่ปรึกษาเห็นด้วย)
- **ระบบตอนนี้ไม่มีปัญหา** (นิ่งดี ไม่มี peak ผิดปกติ) เป้าหมายคือ scale เพื่อรับลูกค้าเพิ่ม + optimize ลดต้นทุน → **Priority = Scale**
- Architecture: MySQL RDS บน AWS, EC2, ทำ Master–Slave (Read Replica); เครื่อง spec 32 core
- ข้อมูล peak: ออนไลน์สูงสุด ~5,271 คน/วัน, คนเล่น/มี transaction จริง ~751–1,000 คน, CPU ตัว Master ใช้แค่ ~20% (≈6 คอร์จาก 32) → เครื่อง over-provision, สเปคเหลือเยอะ
- **ประเมินเบื้องต้น: scale ได้ ~3 เท่า** อย่างปลอดภัย (ไม่เอา 5 เท่าเพราะควรเผื่อ CPU peak ไม่เกิน ~60% กันเครื่อง restart / OS kill process)
- เพื่อพิสูจน์จริงต้องทำ **load test / end-to-end test**: ไล่ flow ผู้ใช้จริง (Login → เลือกเกม → วางเดิมพัน) ยิงทีละ concurrent (เช่น 1,000 cc) ดู CPU/connection ต่อ database; ปัจจุบันมีแค่ unit test (PHP unit test / go test) ยังไม่มี load test และยังไม่มี environment ที่เทียบเท่า production สำหรับเทส
- Sports มีเกมประเภทเดียว (กีฬา) แต่มีหลาย sub-category, ผู้ใช้ 1 คนเล่น/วางเดิมพันได้ทีละเกม (1 activity)
- **ปัญหา concurrency ตอนวางเดิมพัน:** มีลิมิตราคาต่อเกม (เช่น 1,000) หลาย user แทงราคาเดียวกันพร้อมกัน — วิธีปัจจุบันไปอ่าน flag/record ของคนก่อนหน้ามาต่อ ทำให้เกิด low-level lock / read lock และเมื่อกดพร้อมกันเกิด error กับลูกค้าบ่อย (ทั้งที่ยอดยังไม่ถึงลิมิต ควรเล่นได้)
  - แนวทางที่ที่ปรึกษาเสนอ: ใช้วิธี **Insert แล้วนับ/sum** (จำนวนที่แทงรวม) แทนการ read-lock record ก่อนหน้า — เพราะ insert พร้อมกันใน collection เดียวไม่ได้ ยังไงต้องเรียงลำดับเป็น sequence ทำใน cache ได้โดยไม่ต้องแตะ database ถ้าราคาเดิมพันคงที่ (ยังต้องดู algorithm จริงในโค้ดก่อนสรุป)
- Monitoring/Logging ปัจจุบัน: CloudWatch (monitor), Nightwatch (query/response time), SolarWinds (log, ไม่ได้ต่อเข้าระบบ), MySQL slow query log (RDS config)
- **ที่ปรึกษาแนะนำ Grafana**: เวอร์ชันใหม่มี Grafana AI Assistant (open source, ต่อ MCP เช่น MySQL MCP ให้ช่วยวิเคราะห์ slow query / สร้าง index ได้) และชุด **LGTM stack** (Loki, Grafana, Tempo, Mimir) — เป็น all-in-one ประหยัดเงิน เหมาะเมื่อย้ายไป Kubernetes

### 4. Wallet (Thread) — Deploy & Secret Management บน GKE
- โปรเจกต์อยู่บน GKE (Google Kubernetes), แยกเป็นหลาย namespace (API, worker/logจ๊อบ ฯลฯ); Secret ชื่อ `env` (metadata.name = env), format เป็น stringData
- ที่ปรึกษาใช้ Grafana stack เดิม (เวอร์ชันเก่า) จะอัปเดต — คุยเรื่องแชร์ความรู้ Grafana AI/Alloy
- **โจทย์:** ทำ pipeline ให้ตอน deploy validate ตัวแปรใน `config.go` เทียบกับ ENV ใน secret ถ้าไม่ตรง/ไม่มี ให้เตือนก่อนแล้วค่อย approve เพื่อเติมค่าเข้า secret
- **ติดขัด:** ค่า value ของ ENV อยู่ข้างนอก (เครื่อง dev) จะ automate ทั้งหมดไม่ได้ เพราะไม่อยากเอา secret ไปฝากใน secret manager/GitHub ต้องมีคนเป็นคน apply
- 2 ทางเลือกที่คุย:
  1. **Role-based (RBAC + Workload Identity)** — สร้าง IAM บน Google ผูกกับ RBAC ให้เฉพาะสิทธิ์ update secret ใน namespace ที่ระบุ, ใครจะเข้าต้อง login ผ่าน Google IAM ก่อน, dev ส่งไฟล์ให้ผู้มีสิทธิ์ (lead) เป็นคน apply + เก็บ logging
  2. **GitHub Secret + Personal Access Token** — เก็บ secret ทั้งหมดใน GitHub Secret, run ผ่าน PAT ของตัวเอง (แต่ค่าจะค้างอยู่ใน GitHub Secret และ VM runner ตลอด)
- **สรุปเลือกทางที่ 1 (Role-based / RBAC + Workload Identity)** เพราะคุณเบ้นถนัดคุม access control แบบ role-based, และไม่ได้ใช้แค่เรื่อง secret แต่รวมถึงการ log-in เข้าไป debug ดูอย่างอื่นด้วย
- Notification เมื่อ validate ไม่ผ่าน/ENV หาย → เลือกส่งเข้า **Telegram**

### 5. งาน Ad-hoc — Database เต็ม / Sharding (PostgreSQL)
- แจ้งเรื่องจากเมื่อเช้า: database ใกล้เต็ม (sink จะรับไม่ไหว) ต้องทำ **sharding**
- ที่ปรึกษาขอข้อมูลเพื่อวิเคราะห์ก่อน: เข้า Data Explorer → PG Cluster (PG Game) → collection `PG SettleBet` (ตัวที่หนักเพราะ shard/สามเท่า) ขอ **schema (fields), index (size/usage), และ sampling data**
- จะทำ shard เป็น collection; ต้อง analyze สถิติการใช้งานจริงก่อนตัดสินใจว่าควรใช้ index ตัวไหน (ไม่เดา)
- อาจต้องส่ง command สำหรับ analyze ให้ทีมรัน โดยรันช่วง off-peak (การเดิมพันหนักช่วง 5 โมงเย็นเป็นต้นไป)
- Backend team จะเริ่มคุยเรื่อง sharding สัปดาห์หน้า
