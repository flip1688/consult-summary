## เนื้อหาสำคัญ

### 1. ภาพรวม RAG / Knowledge Management
- เป้าหมาย: ทำระบบแชทคล้าย ChatGPT แต่ดึงคำตอบจากข้อมูลเฉพาะขององค์กร (bring your own data) เรียกระบบนี้ว่า RAG = Retrieval-Augmented Generation
- R = Retriever (ดึงข้อมูลที่เกี่ยวข้องขึ้นมา), A = Augmented (นำผลที่ดึงมาประกอบร่าง), G = Generation (ให้ LLM ปั้นเป็นคำตอบ)
- LLM ที่ใช้ปั้นคำตอบเป็นส่วนที่อยู่ "เหนือ" MongoDB เลือกทีหลังได้ (Qwen, local model ฯลฯ) เพราะงานนี้ไม่ต้องการโมเดลฉลาดมาก แค่แปลงผลลัพธ์เป็นภาษา

### 2. Pipeline: Ingest → Chunk → Embed → Index → Generate
- **Ingest:** โหลด/สกัดข้อมูลเข้ามา (เอกสาร, source code, PDF, Word, text)
- **Chunk (ตัดคำ/แบ่งข้อความ):** พี่ฟี่ย้ำว่าเป็นขั้นที่ยากและใช้เวลาที่สุด เพราะขึ้นกับรูปแบบข้อมูล ต้องจูนให้เข้ากับข้อมูลและวิธีค้นของเรา
  - source code สั้น ๆ อาจ embed ทั้งไฟล์; เอกสารยาวอาจ summary ก่อน
  - แบ่ง document ใน MongoDB ให้ไม่ใหญ่เกินไป (เช่นแบ่ง 300 บรรทัด → 200/50/20 แล้วร้อยต่อกัน)
- **Embed:** แปลงข้อความเป็นเวกเตอร์ (ชุดตัวเลข) ด้วย Embedding Model — เป็นโมเดลเล็ก ไม่ใช่ LLM ทำหน้าที่บีบอัดความหมายเป็นตัวเลข
- **Index:** สร้าง 2 แบบคู่กัน
  - Full-text / Keyword Index (เช่น BM25 บน Elasticsearch, หรือ full-text search ของ MongoDB)
  - Vector Index (vector search)
- **ค้นหา (query time):** แปลง query เป็นเวกเตอร์ แล้วหาความใกล้เคียง (similarity) กับเวกเตอร์ในเอกสาร ควบคู่กับ keyword search
- **Hybrid + Reranking:** รวมผลจากทั้ง 2 ทาง ทำ score รวม แล้วใช้ Reranking Model จัดลำดับผลใหม่ให้ตรงเนื้อหา ก่อนส่งให้ LLM ปั้นคำตอบ

### 3. โครงสร้างข้อมูลใน MongoDB (ตัวอย่าง collection "code")
- ฟิลด์ตัวอย่าง: `_id`, `name` (เช่น login.html), `keyword`, `description`, `embedding` (เวกเตอร์ของ description), และถ้าจะ embed โค้ดก็เพิ่ม `sort_code` (source code จริง) + embedding ของโค้ด
- ต้องออกแบบ schema เอง ว่าจะ embed เฉพาะ description หรือ embed โค้ดทั้งก้อน + เก็บ metadata (ขนาดไฟล์, จำนวน function ฯลฯ) เผื่อ query เชิงบริหาร เช่น "ไฟล์ไหนเกิน 100MB / เกิน 1,000 บรรทัด ควร refactor"

### 4. เครื่องมือ (Framework / Library)
- **LangChain** — พี่ฟี่แนะนำเป็นตัวเลือกหลักถ้าใช้ MongoDB เพราะเป็น official support (engineer MongoDB สร้างเอง) มีทั้ง JS/TS และ Python เชื่อม MongoDB Atlas ได้ smooth; จัดการ chunk/embed/index/save เป็น library เรียกใช้ได้
- **Coco Index** — framework สำเร็จรูป (Python) ผูกกับ agent มี MCP ทำ index source code อัตโนมัติทั้งไฟล์ เหมาะเริ่มเร็วโดยยังไม่ต้องเขียนเอง แต่ยังไม่รองรับ MongoDB ตรง ๆ (รองรับ Postgres ฯลฯ) และอาจต้อง customize เยอะ
- **Voyage AI** — embedding model ที่ MongoDB Atlas มีให้ในตัว (Atlas มี hybrid search รวม full-text + vector และทำ score ให้); ถ้าใช้ MongoDB แนะนำใช้ตัวนี้
- **Tree-sitter** — library ทาง compiler/AST สำหรับสกัด syntax ของ source code (parse เป็น tree, เก็บชื่อ function ฯลฯ) กรณีอยาก index code base ละเอียด
- **OpenWiki** — ตัวใหม่ ไอเดียดี (auto-index เป็น wiki, mixed manual ได้) แต่ยัง version 0.0.x ยังใหม่มาก แนะนำรอดูก่อน
- หมายเหตุ: เครื่องมือ text processing ส่วนใหญ่เป็น Python (first-class citizen ด้าน AI) แต่แปลงมาใช้ JS ได้

### 5. การ Update / Retrain Knowledge
- ไม่ใช่การ fine-tune โมเดล (fine-tune = สร้างโมเดลใหม่จาก base model, กินทรัพยากร/GPU สูงมาก ไม่ตอบโจทย์ปัจจุบัน)
- RAG update = เอาของใหม่เข้า / update ของเก่าใน Database
- เทคนิคประหยัด cost: เช็ค hash (md5 — ในถอดเสียงว่า "mdefine") ของ source code เก่ากับใหม่ ถ้าเท่ากัน = ไม่เปลี่ยน ไม่ต้อง re-embed; ถ้าต่างกันค่อย embed + update เฉพาะฟิลด์ที่เปลี่ยน แล้วเปลี่ยน hash เป็น identifier ใหม่
- ถ้าใช้ LangChain / MongoDB Atlas มีกลไก update vector อัตโนมัติให้

### 6. Access Control / Exit Control
- ต้องออกแบบตั้งแต่แรกว่าข้อมูลแต่ละชิ้นให้ใครเข้าถึงได้ (level / team / security เช่น 1BX, "High")
- เวลามีคนถาม chat ระบบต้องรู้ว่าผู้ถามอยู่ level ที่มีสิทธิ์ดูไฟล์/secret นั้นไหม (ตัวอย่างระบบ HR: จำกัดให้ HR ถามข้อมูลลาได้เท่านั้น ถ้าไม่ใช่ตอบว่าไม่รู้)

### 7. Data Source / Connector + แนวคิด Distributed Pre-processing
- ขั้นที่ใช้เวลาจริงคือการ connect แหล่งข้อมูล (โจทย์ยากสุดคือแหล่งข้อมูลอยู่ที่ไหน เข้าถึงยากแค่ไหน มีกี่ประเภท) — ปัจจุบันเอกสาร/knowledge ต่างคนต่างเก็บในเครื่องตัวเอง
- ต้องทำ function/connector ดึงข้อมูล (เช่น Google Drive connector, meet, chat history) มารวมที่เดียว (เช่น Google Drive กลาง หรือเข้า Database เลย) แล้วค่อย chunk/index
- แยกทางเดินได้: โค้ด ใช้ tool ที่ถนัดโค้ดดึงเข้า Database, ไม่ใช่โค้ด เทรวมอีกที่ — สุดท้ายไปเจอกันที่ Database
- **ไอเดียคุมต้นทุน (พี่ฟี่เสนอเป็นทางเลือก ไม่ได้ยืนยัน):** ให้แต่ละ user ตั้ง connector + coding agent (เรียกในที่ประชุมว่า "Co-Work") บนเครื่องตัวเอง กวาดข้อมูลของตัวเองทุกวัน, ทำ pre-processing/embedding ในเครื่องตัวเอง (cost ประมาณคนละ ~$20/เดือน) แล้ว push เข้า MongoDB Atlas กลาง — เพราะ embedding กิน token/cost เยอะ การกระจายภาระ (distributed) ช่วยประหยัด; ส่วน App/หน้าแชท (Agent) พัฒนาตัวเดียวไว้ตอบ ต่อกับ MongoDB
- คำถามที่ยังไม่ชัด: จะทำ connector/plugin ฝังใน coding agent ("Co-Work") แบบ private plugin/marketplace ได้ไหม — ขึ้นกับว่า tool นั้นอนุญาต customize plugin หรือเปล่า (ยังไม่แน่ใจ)

### 8. งาน Consult (ช่วงท้าย)

- ปัญหา Scalability ที่ทีมเจอ: อยาก load test ยิง ~10,000 users จริง แต่ยิงด้วยเครื่องมือเดิม (ในถอดเสียงว่า "Casix" — คาดว่า k6) บนเครื่องเดียว ยิงได้ไม่ถึงหมื่น — ค้างไว้ให้พี่ฟี่ช่วยดูต่อ (ตัดจบช่วงที่ 1 ตรงนี้)
