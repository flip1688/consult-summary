## เนื้อหาสำคัญ

### 1. การวิเคราะห์ Index (MongoDB Atlas – คอลเลกชัน PG Game)
- ดู **usage** ของแต่ละ index จาก Atlas; ค่า `since` บอกว่าเริ่มเก็บสถิติตั้งแต่เมื่อไหร่ (รีเซ็ตเมื่อ restart / ตามรอบ) ต้องดูค่าปัจจุบัน ไม่ยึดภาพเก่า
- คอลเลกชันนี้มีข้อมูลราว **3.2–3.5 พันล้าน document** และมี index ประมาณ **13–14 ตัว**
  - ทุกครั้งที่ insert/update/delete ต้องปรับทุก index → index เยอะทำให้ write ช้าลง
- Index ที่ถูกไฮไลต์ (query ตาม `username`, `bet date`, `bet status`, `create time`) ใช้บ่อยเพราะเป็น query ของ **Report** (มี sort มาก→น้อย)
- มี index ขนาดใหญ่มาก (เกือบ 200 GB) แต่บาง index **usage = 0** → ควรพิจารณาลบ (ดู Performance Advisor ประกอบ) เพื่อคืน storage และเร่ง insert
- Storage รวมเกือบ 500 GB (ใกล้ 1 TB); Data Size จริงราว 14k เฉลี่ยต่อ doc, compression ratio ~1:5 (ลดขนาดได้ ~50%+)

### 2. Shard Key และขั้นตอน Sharding
- แนวโน้ม shard key = `_id` (เป็น ObjectId, unique อยู่แล้ว) แต่ควรใช้แบบ **hashed** เพื่อให้กระจายตัวดี (ObjectId เป็น monotonic ไม่ดีต่อการกระจาย)
- แนะนำเปิดโหมด **configureQueryAnalyzer / analyzeShardKey** เก็บ sampling ~5–10% บน **Staging** ก่อน เพื่อดู key cardinality, การกระจายตัว, ความเป็น monotonic, ค่าซ้ำ/range — ต้องใช้ user ระดับ admin
- แนะนำลองเทียบ **2 key**: key แบบ leading field + key แบบ `_id`
- ขั้นตอนการ Convert (ทำแบบค่อยเป็นค่อยไป บน Staging ก่อน):
  1. Convert Replica Set → Sharded (Config Servers)
  2. Sharded 1 shard (เทียบเท่า Replica Set เดิม)
  3. Add shard + `sh.addShard`, แล้ว `shardCollection` ระบุ namespace `db.collection` + key
  4. ขยายเป็น 3 shard (จำนวนขึ้นกับแผนลูกค้า)
- **ข้อควรระวัง:** convert เป็น sharded แล้ว **ย้อนกลับไม่ได้** (ลดเหลือ 1 shard ได้ แต่กลับเป็น Replica Set ไม่ได้) → ต้องทดสอบบน Staging ให้แน่ก่อน
- คอลเลกชันที่ไม่ได้ shard จะยังอยู่ที่ shard เดิม; มีคำสั่งใหม่ `moveCollection` ช่วย rebalance
- แนวทาง sizing: ปัจจุบัน cluster **M50**. ตอนทำ shard key อาจ bump ชั่วคราวเป็น **M80** เพื่อให้สร้าง shard key เร็ว แล้วค่อยลดกลับ M50 เพื่อไม่กระทบ production

### 3. Online Archive (ปัญหาสำคัญ)
- ตั้งลบ/archive ข้อมูลเก่ากว่า **10 วัน** (อิง `create date` เป็น TTL) — เซ็ตมาตั้งแต่แรก
- กลไก: ทุก ~1 นาทีรัน job, copy ออกแล้ว delete, สูงสุด **100K doc/ครั้ง**; version ล่าสุดเป็น 5-minute job life cycle
- ปัญหา: เมื่อข้อมูลเข้าเยอะ (ถกกันว่า ~100 GB/วัน หรืออาจถึง 500 GB/วัน) **archive ลบไม่ทัน** → storage โตขึ้นเรื่อยๆ
- เหตุผลหลักที่ทำ Sharding = ช่วยให้ **archive/ลบข้อมูลเร็วขึ้น** (data partition, แต่ละ shard รันคนละ job ขนานกัน) นอกเหนือจากเรื่อง insert เร็ว
- Rule of thumb: เข้า ~100 GB/วัน เริ่ม **2 shard** พอ; ~500 GB/วัน ต้อง **3–4 shard**. เคสก่อนเคยต้องเขียน script ลบเองเพราะ archive ลบไม่ทัน
- **พบว่า Online Archive กำลัง FAIL ตลอด** (Last Archive Running error) → ข้อมูลไม่ถูก archive เลย, storage จึงโต ต้องตรวจว่าซื้อ Pro Support หรือไม่เพื่อสอบถาม error กับ MongoDB Support
- วิธีเชื่อมต่อดูข้อมูลที่ถูก archive: เมนู 3 จุด / sidebar **Online Archive** → Connect (read-only) ผ่าน Compass/Driver/Shell

### 4. Load Testing (คำถามน้องโก – โปรเจกต์ใช้ PostgreSQL, ยังอยู่ dev/test)
- แนะนำ **K6** (open-source ของ Grafana); เวอร์ชันใหม่มี AI assistant ช่วยเขียน script + มี Studio; ใช้ผ่าน Grafana Cloud free ได้ (มี simulation จำกัด)
- เขียน scenario (login, ยิง request) เป็น Node.js style; ผูกกับ Grafana ดูผลได้
- ถ้าไม่มี load test เฉพาะ DB → ยิงแบบ end-to-end ผ่าน API/APM
- ตัวชี้วัดที่ควรอ่าน: **P95 Response Time**, **Requests/sec**, ช่วง peak, อัตรา fail (ดูจาก Performance Overview)

### 5. Logging / Monitoring / Tracing
- สถานะปัจจุบัน (โค้ด Go): แค่ **print log** ออก stdout → เก็บที่ **GCP Cloud Logging**, ดูผ่าน Logs Explorer (มี line number ให้อัตโนมัติ), ไม่ได้ใช้ Open Telemetry/library ใดๆ
- ความเสี่ยง: log **tag SQL ทุกคำสั่ง** → ข้อมูลสำคัญ/ส่วนตัวหลุดออก log (ทุกคนที่เข้าถึง log เห็นได้) — ควรทำ **masking** หรือใช้ library ช่วย
- คำแนะนำ:
  - ทำ **audit toggle** (feature flag / secret key) เปิด-ปิด log ละเอียดโดยไม่ต้อง redeploy — เปิดเฉพาะตอนต้อง audit จริง เพื่อประหยัด storage/process
  - จับ 2 เรื่องเวลา error: (1) function/file/บรรทัดที่พัง + สาเหตุ (2) เวลาแต่ละ function/API ที่ต่อเนื่องกัน (performance trace)
  - ใช้ **Open Telemetry + Jaeger** สำหรับ tracing/performance (ดู flow ของ function เป็น millisec)
  - ระวัง log storage โตไม่มี rotation (log อยู่บน VM ก่อน flush ยิ่ง audit ละเอียดยิ่งกิน storage)
- กรณีอยากเอา log/activity มาโชว์บน **UI ให้ admin ดู** (เช่น log การเดิมพัน):
  - ถ้าเน้น consolidate ต่อ activity: เก็บ JSON embed ต่อ activity ใน Mongo/Postgres/BigQuery แล้วดึงทั้งพวงมาแสดง
  - ถ้าต้องการ speed insert สูงสุด: insert แบบ event ลง store เร็วๆ (เช่น ClickHouse) แล้วทำ report
  - หรือใช้ **Grafana + Prometheus (time series)** ทำ report แล้วให้ admin login ดู
  - **อย่า expose log สาธารณะ** เป็นช่องความเสี่ยงด้าน security

### 6. CI/CD – GitHub Actions (นำเสนอโดยพี่ฟี่, ทดสอบบน Go แล้ว work)
- Pipeline ใช้ **Workload Identity Provider**: `Code Compare` เทียบค่าใน `config.go` กับ **secret ใน kube secret** — ถ้า key ไหน missing ให้ fail หยุด pipeline
- ผลลัพธ์ report (found in go / found in secret / mismatch: missing, extra) ยิงแจ้งเข้า **Telegram**
- **RBAC script** (YAML): สร้าง Role → RoleBinding ผูกกับ user/service account เพื่อได้ log ว่า "patched by ใคร"
- Secret ควบคุมใน kube secret 100%; แนวคิดให้ dev แต่ละคนมี **Service Account** ต่อ cluster, ผูกด้วย **Workload Identity** (ระดับ Google IAM) เพื่อ control หลาย cluster/project
- แนวทาง automation: ใช้ **Argo CD** / pipeline สร้าง Service Role อัตโนมัติเวลาสร้าง cluster; flow ให้ User request → review → apply → deploy ลง GKE อัตโนมัติ

### 7. Infrastructure as Code – Terraform vs Pulumi
- แนะนำไปทาง **Terraform** (คนใช้เยอะ) — เป็น template แยกชิ้น (module) ได้, up/down, `init/plan/apply`, plan = dry run ตรวจก่อนสร้างจริง
- ทางเลือก **Pulumi**: เขียน infra เป็นโค้ดจริง (Python/Go/…) มี SDK, dry run/simulate, state, up/destroy, แก้เฉพาะส่วนได้ — ข้อดีคือใช้ **ภาษาเดียวกับทีม** ลด learning curve
- **HCP (Terraform Cloud)** ไม่จำเป็น — ราคาแพง (enterprise), มี limit feature
- ทั้ง Terraform/Pulumi ผูกกับ pipeline (GitHub Action หรือ Argo CD) เหมือนกัน; GitHub ไว้เก็บ version
- Terraform เก่าใช้ HCL รุ่นเก่าถูกยกเลิก ต้องใช้ YAML/รุ่นใหม่ (บางคนไม่ถนัด → Pulumi เป็นทางเลือก)
