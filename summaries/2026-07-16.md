## เนื้อหาสำคัญ

### 1. ภาพรวมและโจทย์ของระบบ
- โจทย์: รวมข้อมูลที่กระจัดกระจาย (เอกสาร + โค้ด) มาเป็นแหล่งเดียวที่ Chat คุยถามตอบได้ ตอบได้ทั้งภาษาไทยและอังกฤษ (ภาษาไทยกิน token มากกว่าเล็กน้อย)
- ระบบมี Login (แบบง่าย) และเก็บข้อมูลบน Database (MongoDB) แล้ว
- ตอบเป็นภาษาไทยได้เพราะผ่าน LLM (RAG generate) โดยยังต้องอาศัย keyword จริงในการค้น ถ้าไม่พบข้อมูลในระบบจะตอบว่า "ไม่พบ" ไม่ออกไปค้นนอกขอบเขต (scope ควบคุมได้)

### 2. Agentic Flow / การทำงาน
- เป็น Agentic RAG: agent มี tool หลังบ้านหลายตัว หลัก ๆ 2 ตัวคือ Resource (ดึงข้อมูล) และ Search แล้วเลือกเครื่องมือเอง (tool selection) แต่ไม่ได้ฉลาด 100% จึงต้อง scope ให้ เช่นถ้าเป็น PDF ให้ไป tool จัดการ PDF, ถ้าเป็น GitHub ให้ไป tool จัดการ GitHub
- มี Thinking Process แสดง step ให้เห็นว่า agent เรียก tool ตัวไหน ค้นที่ไฟล์ไหน (query ไป PDF และ query ไป Git ต่อเนื่องกัน) — เรียกรูปแบบนี้ว่า Agentic Loop (agent มากกว่า 1 ตัว + add skill/add tool ได้)
- Knowledge Base ปัจจุบันประกอบด้วย Git repo (ดึงจาก public repo) และไฟล์ PDF (upload เข้าไปให้สกัดข้อมูล)

### 3. เทคโนโลยีและสถาปัตยกรรม
- Frontend: Next.js / Backend: FastAPI (Python) — โค้ดผสม TypeScript + Python เพื่อให้ทำ demo ง่าย
- LLM ตอบคำถาม: GPT-5.2 ผ่าน Azure/Microsoft Foundry
- Embedding: ใช้โมเดล embedding (voyage 4 ตามบริบท) ราคาถูก
- Database: MongoDB (รันบน Podman/Docker บนเครื่องตัวเอง) — เก็บเป็น chunk พร้อม metadata
- Index 2 ชุด: Vector index (embedding) และ Text index (keyword) โดยฟิลด์ที่ทำ vector เช่น source/title/text
- Chunking: ตัดประมาณ 1,000 ตัวอักษรต่อ chunk มี overlap 150 (ให้ index ต่อเนื่อง smooth) — Auto Embedding (ไม่ต้องจัดการ insert เอง)
- Limitation: cap 25 MB ต่อ PDF, chunk ต่อ repo สูงสุดราว ๆ ที่กำหนด

### 4. Hybrid Search ด้วย MongoDB `$rankFusion` (Lang Fusion)
- ใช้ operator `$rankFusion` (มีใน MongoDB v8 ขึ้นไป) รวมผลลัพธ์ vector search + keyword search อัตโนมัติ
- ให้น้ำหนัก (weight) vector สูงกว่า keyword (ราว vector = 2, keyword = 1)
- Candidate: ใช้หลัก "คูณ 3" — ถ้าต้องการ retrieve 10 ก็ตั้ง candidate มากขึ้น (คูณ 3+) เพื่อค้นครอบคลุมกว่า
- ผลลัพธ์คืน text, source/location, doc type มาแสดงบน UI เป็น "หลักฐาน" ว่าดึงมาจากไหน
- ค่า setting ทั้งหมด (ชื่อ DB, model, index vector/text, chunk size, overlap, weight, candidate) อยู่ในไฟล์ config/ENV ปรับได้

### 5. Memory (Short / Long / Working) — ประเด็นที่ยังพัฒนาไม่เสร็จ
- ระบบปัจจุบันยังไม่มี Memory (เน้น RAG ก่อน) เป็นสิ่งที่จะเสริม
- Short Memory: บทสนทนาแต่ละ chat, ทำ TTL index ให้ลบทิ้งอัตโนมัติเมื่อครบเวลา
- Long/Working Memory: เก็บ pattern/วิธีการแก้ปัญหาของแต่ละคน ซึ่งไม่มีในเอกสารหรือ source code (ไม่ใช่ Knowledge Base)
- แนวคิด flow 3 step: Short → สรุปเป็น Long Term (summary) → ถ้าควรเป็นความรู้ถาวรให้ convert เป็น Knowledge (เขียนเป็น blog/wiki) แล้วลบออกจาก Memory เพื่อไม่ให้เป็นขยะ
- หลักการ: Database/Knowledge Base คือแหล่งความจริงที่ต้อง update เรื่อย ๆ, สิ่งที่บันทึกใน Knowledge แล้วไม่ควรค้างใน Long Memory (พี่ฟี่กำลังเรียน/ทำเรื่อง Agentic Design อยู่)

### 6. แนวทางต่อยอด: MCP / Integration กับ Code Agent
- บี (B) อยากได้เป็น MCP มากกว่าเว็บแชท เพื่อเสียบเข้า Claude Code / VS Code เป็น skill ให้ค้น knowledge ในโฟลเดอร์ + ค้นในคลังกลาง แล้ว agent planning และแก้โค้ดต่อได้
- เนื่องจาก backend เป็น API อยู่แล้ว สามารถทำ MCP server (เพิ่ม SSE/server-side) ต่อยอดจาก endpoint เดิม หรือทำเป็น Skill ที่ link เข้า API ได้ตรงไปตรงมา
- Tool Register: แยก function ตาม category/catalog (เช่น query เฉพาะ Project B, เฉพาะ Ticket) เพื่อให้ agent เลือก tool ที่ specific ขึ้น ลด performance ที่สิ้นเปลือง
- แนวคิด "ครบลูป": ให้ agent push code / ทำ action ได้ผ่าน MCP (เช่น One Box Push) แต่ต้องมี Human-in-the-loop คอนเฟิร์มก่อน ไม่ push อัตโนมัติ

### 7. เปรียบเทียบกับ OpenClaw / th call และวิสัยทัศน์ Product
- OpenClaw (และ th call ของคนไทยที่ "หมอจิม" manage) ทำงานใน layer ที่สูงกว่า (PaaS) จัดการ memory ให้หมด แต่ไม่รู้กลไกข้างใน
- สิ่งที่พี่ฟี่ทำคือ Fundamental / Infrastructure-level (สร้าง OpenClaw จากศูนย์) เพื่อให้เข้าใจ data layer, long/short term memory และปรับแต่ง/แกะได้เองแม้ tool ตัวหน้าเลิก support
- Product ใหม่ชื่อ "Magenta" (Agentic Framework/Platform 100%) ของ MongoDB ที่กำลังจะออกช่วง Q4 (ราวกันยายน-ตุลาคม) — เพียงใส่ data layer/backend ก็ครอบ management ให้ (พี่ฟี่เห็น demo แล้วแต่ยังไม่ได้ใช้จริง)
- ปัญหาเฉพาะภาษาไทย: ต้องคิดเรื่อง vector size / embedding เพิ่มเติม
