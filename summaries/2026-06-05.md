## เนื้อหาสำคัญ

### 1. Use Case และ Sequence Diagram (ช่วงต้น — 1BX)
- "หนู" ทำ Use Case ของหน้า Member / Agent / Admin เสร็จแล้ว รวมถึงจัดการ UI state (จนกว่าจะหมด state) และเริ่มลอง Sequence Diagram แบบ Markdown ให้ VS Code (V8 code) ช่วยทำ แต่ยังทำแค่บางส่วนหลัก
- หน้า Agent มีการปรับ logic/state ใหม่เยอะ จึงต้องกลับไปปรับ Use Case ตัวนี้
- พี่ฟี่แนะนำว่า **ควรทำ Sequence Diagram ให้ครบทุก Use Case** เพราะช่วยแตกขั้นตอนการทำงานของแต่ละ Use Case ให้เห็นว่าโปรแกรมที่เขียนทำครบขั้นตอนจริงหรือไม่ และช่วยให้ทีม (รวมถึงคน non-technical) สื่อสารเข้าใจตรงกันเรื่องความยากง่ายของงาน
- แนวคิด: ไล่จากภาพใหญ่ (PID) → Use Case → Sequence ลงรายละเอียดเหมือนซูมแผนที่ ถ้าเวลาจำกัดให้เริ่มจากส่วนหลักที่ต้องเข้าใจจริงก่อน

### 2. Testing Pyramid / Test Framework
- อธิบายพีระมิด: แกน More Integrated (บน, ทดสอบร่วมกับระบบอื่น, ช้า) vs More Isolated (ล่าง, ทดสอบแยกเองได้, เร็ว)
- ชั้นต่าง ๆ:
  - **Unit Test** — หน่วยเล็กสุด แต่ละฟังก์ชัน/ขั้นตอนทดสอบเองได้ (map กับแต่ละ step ใน Sequence)
  - **Component / Module Test** — กลุ่ม Unit Test ในโมดูลเดียวกันที่ทำงานร่วมกัน (เช่น ฝากถอน 3 ขั้นตอน: เช็กยอด, เคลียร์, issue ticket) — จำเป็นน้อย อาจ ignore ได้
  - **Integration Test** — ทดสอบ flow ที่ร้อยเรียงข้ามฟังก์ชัน/ข้ามระบบ (2 service join กัน)
  - **API Test** — เน้น Controller/Endpoint หลังบ้านเส้นเดียว (input → output) ไม่ยุ่ง UI
  - **UI Test / E2E** — End-to-End จาก action ข้างนอกวิ่งเข้าทุกโมดูล ทำ manual ก็ได้ ช้าสุด
- **Test Coverage** — สแกนโค้ดว่าครอบคลุมกี่ % หลังยิงเทส ใช้ดูว่าขาดเคสไหน
- AI สามารถ generate Test Scenario/Test Case พื้นฐานจาก Requirements / Sequence / Use Case ได้ ให้คนแค่ review ว่าถูกต้อง

### 3. สถานะปัจจุบันของทีม (OMBED / Thread)
- Unit Test: ใช้ **Go test** เฉพาะ logic การคำนวณทางคณิตศาสตร์ (เช่น bet/คำนวณยอด) — ตั้งค่าให้แสดงแค่ pass (ขึ้นเขียว) ยังไม่ได้ดู coverage
- API: ใช้ **Postman** ทดสอบด้วยมือ (ยังไม่ automate)
- UI: ทดสอบแบบ Manual (คลิกเอง)
- ฟีเจอร์เก่าหลัก ๆ มี test บางส่วน แต่ของใหม่ที่เขียนขึ้นมามักไม่มี test เพราะเดิมต้องเร่งส่งงานเร็ว ไม่มีกฎบังคับให้เขียน test

### 4. เครื่องมือ Automation ที่แนะนำ
- UI/E2E: **Playwright** หรือ **Selenium** (มีความสามารถ record → ทำ automation ได้)
- API: **Postman** (มี CLI/Newman ทำ automation), หรือใช้คู่กับ Selenium
- CI/CD: **GitHub Actions** (Microsoft) ฝัง test step เข้าไปในกระบวนการ deploy
- แนวทางที่พี่ฟี่ชี้: พยายามแปลงงาน Manual Test ทั้งหมดเป็น Automation ให้มากที่สุด เพื่อ rerun ได้ตั้งแต่ Day 1 ถึง 3 เดือนโดยผลไม่เปลี่ยน

### 5. โมเดล CI/CD ที่ออกแบบร่วมกัน
- Dev เขียนโค้ด + Unit Test มาพร้อมกัน → push → เข้า QA branch → Staging → คน Approve → Production
- ก่อน push มี **hook** เช็กว่ามี test file ครบไหม (คล้ายที่เคยทำ hook ตรวจ commit)
- GitHub Action validate: รัน Go test ต้อง pass ครบตามจำนวนที่ระบุ (เช่น 5 ข้อ) ถ้าไม่ครบให้ Noti/หยุด
- ต้องมี **information/spec** ส่งขึ้นไปเทียบ (จำนวนเทสที่ต้อง pass, Scenario UI ที่ต้องผ่าน) เพื่อ compare ครบ/ไม่ครบ
- แนวคิดไฟล์ `test.md` (Markdown) วางที่ root ของ repo (ระดับเดียวกับ `.github`) ระบุรายชื่อไฟล์ `_test` ทั้งหมด → เขียน script รันทุกบรรทัด ถ้าไฟล์ไหน fail ก็ไม่ไปต่อ
- ควรเก็บ **Report/History** ของผลเทสไว้ใน GitHub Action เป็นหลักฐานว่าทุก push เดิมที่เคย pass ยังคง pass (จับ regression เวลาเปลี่ยน version/library)
- ทำ 2 ขั้น: (1) รันบนเครื่อง Developer ก่อน (commit hook/local script), (2) รันซ้ำบน Staging ก่อน Approve

### 6. เจ้าของงาน Integration Test
- Unit Test เขียวทุกตัวไม่การันตีว่าเอามาต่อกันแล้วถูก (Dynamic input/output ระหว่างฟังก์ชัน) — Integration/API Test คือส่วนที่จับ regression ของ Business Logic
- Integration Test ควรทำโดยคนที่เห็นภาพรวม (Senior Dev / Lead) ไม่ใช่ Dev ที่ทำแค่ Unit ของตัวเอง — เพราะต้องรู้ว่าจะร้อยหลาย Unit เข้าด้วยกันอย่างไร
- ถ้าปรับโครงสร้างทีมได้ก็ทำแบบทีม Wallet; ถ้าไม่ได้ก็ให้ Senior คุม โดยให้ Dev ทุกคนเห็น overview ระดับ BA ของโปรเจกต์
- ปัญหาที่ถกกัน (โดนัด/Sports): microservices + message queue (FQ) ที่ร้อยเรียงกัน, การ provision DB/service หลายตัวเพื่อ Integration Test ช้าและกิน resource
- แนวทางที่เสนอ: เตรียม Environment ทิ้งไว้ (Database, MQ, service เวอร์ชันที่ผ่าน QA แล้ว) provision เฉพาะ service ที่กำลังแก้, seed data ใหม่ต่อรอบเพื่อเลี่ยงปัญหา data ซ้ำ (เช่น register user), ให้ Test Server/Pipeline รัน Integration ให้แทนที่จะให้ Dev รันบนเครื่องตัวเอง

### 7. Third-Party Certified Tester
- บางอุตสาหกรรม (เช่นธนาคาร / PCI) ต้องการ Report จากบริษัททดสอบที่มี Certification (เช่น ISTQB) หรือใช้เครื่องมือมาตรฐานเช่น **Burp Suite** ที่ออก report ตาม license
- เหตุผลไม่ใช่เพราะ Dev ในทีมทำไม่ได้ แต่เป็นเรื่อง "กระดาษรับรอง" / การการันตีโดยหน่วยงานภายนอกที่ได้รับการยอมรับ
