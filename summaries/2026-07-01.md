## เนื้อหาสำคัญ

### 1. ความต้องการด้าน Knowledge Base (3 ข้อ)
ผู้เปิดประเด็น (ฝั่ง Wai) สรุปว่าอยากได้ 3 อย่างในยุค AI:
1. **ทำให้ workflow ลื่นไหลขึ้น** โดยเฉพาะการ share knowledge — ปัจจุบันข้อมูลอยู่ในหัวแต่ละคน (BA/QA, Designer, Dev, Project Co) พอเล่าต่อกันข้อมูลตกหล่น อยากให้ทุกคนเห็นทุกการตัดสินใจที่ push เข้า project (เช่น feature ไหนถูกตัดทิ้ง Dev ควรรู้)
2. **ที่เก็บ knowledge กลาง** — คนอื่นเก็บกันยังไง ควรมีระบบสิทธิ์การเข้าถึง (บริหาร access ตาม level เช่นข้อมูลผู้บริหาร Junior ไม่ควรเห็น)
3. **พื้นที่ demo งานกลาง** — ปัจจุบันต่างคนต่างมี Vercel/พื้นที่ของตัวเอง กระจัดกระจาย อยากมีที่กลางสำหรับ demo (งาน HTML/JS/CSS static)

### 2. แนวทางของ บี (playbook/runbook + Notion)
- เก็บ knowledge เป็นไฟล์ MD, ให้ AI สัมภาษณ์/สรุปเป็น MD แล้ว push ขึ้นเป็น Knowledge พร้อม tag (เช่น tag "playbook/runbook")
- ทุกครั้งที่ solve ปัญหาเสร็จ → AI สรุปเป็น MD + อัปเดต memory + จดลง Notion ของตัวเอง พร้อมติด tag ให้ค้นง่าย
- ตัวอย่างการใช้จริง: subnet/IP calculation, การตั้ง runtime zone ใหม่ ให้ AI อ่าน note เดิมแล้วจัดการให้เลย
- ปัญหา: ทำคนเดียวสวยงาม แต่ scale ให้ทีมยังทำไม่ได้ / ยังไม่ orchestrate ทั้งกระบวนการ

### 3. สถาปัตยกรรมที่ที่ปรึกษาเสนอ (RAG / Ask-Expert)
- ภาพรวม: **DataSource + LLM + RAG** โดยรวมข้อมูล (Database, PDF, Notion, GitHub repo) ไว้ที่ศูนย์กลางก่อน แล้วทำ Index → ต่อเข้ากับ "หน้ากาก" (front-end UI) ที่ผู้ใช้ chat ได้
- แนวคิด "Ask Expert" แยกตามเรื่อง (คล้ายที่บริษัทที่ปรึกษามี Ask HR / Ask Noon เป็น Telegram bot) — จำกัด scope ต่อ Data ที่ต้องการ
- **Local Model** (เช่น GLM 4.5/4.6, Gemma) ทำหน้าที่แค่ "ปั้น" คำตอบให้อ่านง่าย ไม่ต้องพึ่ง frontier model เพื่อประหยัดค่า token; lock spec ให้ตอบเฉพาะจากข้อมูลใน index เท่านั้น ("ถ้าไม่มีให้บอกไม่รู้")
- **Access control / sensitive data:** ให้ login เพื่อ classify data ตาม level (เช่นถามเงินเดือนเพื่อน = ไม่ให้เข้าถึง) กันตั้งแต่ตอนทำ index
- **Google Drive กลาง:** ถ้ามี Share Drive ระดับองค์กร ให้สร้าง folder กลาง โยนงานเข้าไป แล้วให้ระบบทำ index อัตโนมัติ — แต่ยังต้องมี Connector มาจัดการดึงข้อมูล/ทำ metadata (tag/summary ต่อเอกสาร) เก็บลง DB (เช่น MongoDB) เป็น vector; ตอน search จะ match summary → ค่อยดึง content จริงจาก PDF ผ่าน skill (ไม่ต้อง copy ข้อมูลทั้งหมดลง DB คงไว้ที่เดิม)
- **MongoDB Agentic Platform:** ที่ปรึกษาบอกใบ้ว่า MongoDB กำลังจะออก platform agentic (ยังไม่ประกาศ อาจปลายปี) + **Voyage AI** สำหรับ embedding/chunking (free 200M token) — สอดคล้องแนวทาง Bring Your Own Data Source
- **Tooling หน้ากาก:** Anything LLM (open source, เป็นแค่หน้ากาก config ต่อ MCP) หรือใช้ **Cursor** แทนก็ได้ (มี automation ในตัว แค่สร้าง skill มาต่อ) — ประเด็นสำคัญคือ Connector และการ index ต่างหาก ไม่ใช่หน้ากาก
- **MCP connectors:** เช่น MongoDB MCP (สาธิตต่อ DB ถามว่ามี query ช้า/index กี่ตัว), Notion MCP; ระวังเรื่อง OAuth/สิทธิ์การเปิด connector รายเครื่อง

### 4. Code Agent สำหรับ Code Base
- แรงจูงใจของ โด/โดนัท: เวลา Dev หายหรือเจ้าของงานลาหยุด ต้องมานั่งไล่โค้ดทั้งโปรเจกต์ อยากได้ตัวช่วยที่เป็น "หลีดของ codebase" ช่วย support case; MD/AGENTS.md อย่างเดียวไม่ลงลึกพอ source of truth ยังเป็นตัวโค้ด
- ที่ปรึกษาแนะนำ: **ไม่ควร index ทั้ง codebase** แต่ทำ index อีกแบบ — ทุกครั้ง push/merge → trigger automation ทำ **summary ต่อไฟล์/ฟังก์ชัน** (ไฟล์นี้มีกี่ฟังก์ชัน แต่ละฟังก์ชันทำอะไร) เก็บเป็น metadata/vector ใน MongoDB; local model แค่ search + แปลผลให้มนุษย์
- ต้อง **design ร่วมกับ Team Lead** ว่าจะอธิบายฟังก์ชันยังไง (Agentic Design) และอาจต้อง **refactor/จัด style โค้ด** ให้ AI อ่านง่าย (บางส่วนอาจทำ manual สำหรับโค้ดที่ไม่ยุ่งมาก)
- Level 1 = ชี้ว่าปัญหาอยู่ไฟล์/บรรทัดไหน; Level 2 = แก้ให้เลย (ต้องใช้ Code Agent จริง + frontier provider เฉพาะตอน implement ท่าใหม่ๆ)
- **Framework:** LangChain vs Mastra (Master AI) — ถ้าใช้ MongoDB เป็น memory, LangChain ตอบโจทย์สุด (มี official plugin เป็นพันธมิตรกัน); โด ถนัด TypeScript จึงขอให้ที่ปรึกษา compare LangChain JS vs Python (Python นำหน้าเรื่อง ingestion/embedding) และ compare กับ Mastra
- Local model รัน code agent ต้องใช้ RAM สูง (~128GB) — อาจต้องตั้ง VM/ระบบกลาง

### 5. Security Review — OMBED Wallet (ทีม Thread)
- **สถาปัตยกรรม:** Frontend static (CDN + bucket แบบ S3, client-side render) → Google Load Balancer → K8s Ingress/Gateway → Microservices (namespace เดียวกัน) → Cloud SQL (Postgres) / Memorystore (Redis)
- **Auth ปัจจุบัน:** JWT (หมดอายุ ~20-30 นาที), token exchange, มี CORS origin check
- **ข้อเสนอที่ปรึกษา — 3 layer ที่ Gateway:** (1) **Lock IP** (Static/Reserved IP ของ frontend ที่ Load Balancer / allow-list) (2) Origin check (3) API Key/JWT — เพราะ Gateway เป็นจุดเดียวที่ public ถ้าคนรู้ชื่อ (เช่น `api.ombed.com`) ก็ยิงตรงด้วย Postman ได้ ต้อง lock ต้นทางให้ชัด
- **Database:** Cloud SQL ควรเปิด firewall/Access Control ให้เฉพาะ Private IP ของ microservice / ใช้ Cloud SQL Auth Proxy; ไม่เปิด public; พี่โด ใช้ VPN + proxy เข้า DB อยู่แล้ว
- **PgAdmin/Console บนเว็บ:** เสี่ยงถ้า public → เพิ่ม layer login (nginx auth) หรือ IP allow; บี แนะนำ **Google IAP (Identity-Aware Proxy / TCP Tunnel IAP)** เป็น proxy กั้นก่อนถึง DB
- **MQ (message queue):** อยู่บน AWS ขณะที่ workload อยู่ Google Cloud — prod ไม่เปิด public ต้องทำ private network / site-to-site (อาจย้าย consumption ไป AWS)
- **PSC (Private Service Connect):** ใช้เชื่อมแบบ private เมื่อ DB ไม่เปิด public IP; เปลี่ยน DB port จาก default (5432) เพื่อเพิ่มความยาก
- หลักการรวม: ปิดทุกอย่างเป็น private ให้หมด เปิด public เฉพาะ Gateway + client site

### 6. Security Review — Logic ฝาก-ถอน & หวย (ทีม Thread)
- UC13 ฝาก-ถอน, แยกฟังก์ชันเป็น UC64/UC69; เครดิตเป็น "กระเป๋ากลาง" ต่อ user (ไม่ใช่ pot รวม), 1 คนเล่นได้ 1 เกมต่อเวลา
- **ช่องโหว่ที่ที่ปรึกษาชี้:** `PostTransaction` รับแค่ 3 params (type=deposit, amount, member) และ **ไม่มี "หัวสาย" (upline)** ใน parameter — ถ้า Member ID เดา/ปลอมได้ อาจ deposit เงินตัวเองมั่วได้ ทีมชี้แจงว่า upline แกะจาก token แล้วเช็ค แต่ที่ปรึกษาย้ำว่าเรื่องเงินต้อง Security First
- **ข้อเสนอ:** lock IP ที่ Load Balancer เป็นอันดับ 1, encrypt JWT อีกชั้น (JWT decode payload ได้แม้แก้ไม่ได้), ไม่พึ่ง domain switching อย่างเดียว (subdomain per agent เป็นแค่การทำให้งง ไม่ใช่ security จริง)
- **ปรับเครดิต:** เป็นการ reset/adjust เครดิตเฉพาะ user คนนั้น ไม่กระทบ pot รวม → ไม่มี race condition ข้ามคน (เคลียร์ข้อกังวลเรื่องปรับเครดิตพร้อมมีคนถอน)
- **คาดคะเนได้เสีย:** เป็น report การเดิมพัน (หวย) แบบ real-time; **logic ใหม่** = ตั้งค่าอัตราจ่ายแบบขั้นบันได โดยทำเป็น "กลุ่มการตั้งค่า" (เช่น 3 ตัวบน/2 ตัวบน เปอร์เซ็นต์/อัตราจ่าย) แล้ว assign ให้ประเภทหวย (หวยรัฐบาล/หวยลาว)
