## เนื้อหาสำคัญ

### CI/CD ด้วย GitHub Actions (เดโมโดยพี่ฟี่)
- สาธิตการสร้าง **Environment** (production / staging) ใน GitHub repo settings แล้วผูก **Secret** (ค่าไม่ถูกเปิดเผยตอน build) กับ **Variable** (ค่ามองเห็นได้) แยกตามแต่ละ environment เพื่อแยก config เช่น connection string ของ prod/staging ให้ชัดเจน
- ตั้ง **Required reviewers** ต่อ environment ให้ต้องมีคน approve ก่อน deploy; ติ๊กห้าม self-review เพื่อบังคับให้คนอื่นเป็นผู้อนุมัติ
- Flow ที่แนะนำ: build → deploy staging → tester ทดสอบ → คน approve → build/deploy production (ใช้ image เดิม tag เป็น production)
- แต่ละ job แยกกันทำให้ **rerun เฉพาะ job ที่ fail** ได้ง่าย และใช้ `needs`/เงื่อนไข dependency ให้ job production ทำงานได้ก็ต่อเมื่อ job staging สำเร็จ
- job จะไม่ถูกรันหาก reviewer ยังไม่กด approve

### เคสของคุณเบ้น (setup ปัจจุบัน) และข้อเสนอปรับปรุง
- ปัจจุบันคุณเบ้นมี **YAML 2 ไฟล์ + 2 branch (staging / production)** ต้อง push 2 รอบ: dev push staging → tester ทดสอบ → คุณเบ้น merge เข้า production เอง
- ยืนยันว่าที่ผ่านมา push ผ่าน staging แล้วแทบไม่ต้องกลับไปแก้ code อีก (โดยปกติผ่านแล้วขึ้น production ได้เลย)
- พี่ฟี่เสนอให้รวมเป็น **flow/pipeline เดียว**: push staging → approve → ระบบ deploy production ต่อให้อัตโนมัติ โดยไม่ต้องให้ dev push code ซ้ำ (แม้ยังคงเป็นคนละ branch คนละ tag/versioning ได้ ผ่านการกำหนด scope ใน pipeline)
- แนะนำใช้ **reusable workflow (template กลาง)** ของ GitHub Actions เมื่อ staging/production มีขั้นตอนเหมือนกัน ต่างแค่ environment/parameter จะลด code ซ้ำและลดการต้องแก้หลายที่เวลาเพิ่มขั้นตอน (เช่น เพิ่ม UAT)

### การจัดการ ENV / Secret เมื่อมีการเพิ่ม parameter
- ปัญหา: เวลาเพิ่ม DB/secret ใหม่ ต้องไปเพิ่ม GitHub Secret มือทั้ง prod และ staging
- พี่ฟี่เสนอแนว **Platform Engineer**: ทำ automation ผ่าน **GitHub API** (เช่น shell script อัปโหลด secret) แทนการวาง secret ไว้ใน repo แล้วให้ automate ดึง (เสี่ยงเกินไป) โดยให้แต่ละคนใช้ token/สิทธิ์ของตัวเอง
- การเช็คว่ามี ENV ครบก่อน push/commit: แนะนำใช้ **Git hook / pre-commit** (เทียบเคียง Husky) ตั้ง validate rule ให้ commit/push fail ทันทีถ้าขาด ENV; ทำได้ทั้งฝั่ง client (pre-commit) หรือใน pipeline (validate job) — พี่ฟี่จะหาชื่อ/วิธี set มายืนยันภายหลัง

- ไอเดียที่อยากทำแต่ยังไม่ได้ทำ: **auto-scale ตัว Lotto** ซึ่ง peak เฉพาะช่วงหวยออก (วันที่ 1 และ 16) — อยากตั้งเวลาเพิ่ม spec/replica ก่อนวันออก 2 วันแล้วลดกลับ
- พี่ฟี่แนะนำให้เอา infra code ขึ้น Git เพื่อ versioning/ความปลอดภัย/รองรับทีมโตขึ้น และเสนอให้คุณเบ้นแชร์ script ที่มีอยู่มาให้ช่วยรีวิว/จัดรูปแบบให้เหมาะกับอนาคต (อาจเป็น Terraform หรือ cron job — ยังไม่ตัดสินใจ standard)
