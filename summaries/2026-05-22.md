## เนื้อหาสำคัญ

### 1. การทำเอกสาร API — Swagger/OpenAPI vs Postman
- ทีมทำ API preview ออกมาแล้ว (back-end ทำ API ไว้) แต่ยังมี error บางส่วนจากตัวที่ PC เขียนให้
- Postman กับ Swagger ต่างใช้มาตรฐานเบื้องหลังเดียวกันคือ OpenAPI; Postman สามารถ export เป็น API spec ได้
- ที่ปรึกษาแนะนำ: ถ้าไม่ได้เน้นส่งมอบเอกสารตามมาตรฐาน ให้เลือกได้ 2 แบบ
  - ใช้ Swagger Design ก่อน เพื่อสื่อสาร High-Level ระหว่าง Business กับ Function (เห็นภาพว่า business ร้อยเรียงเป็น API อย่างไร)
  - หรือใช้ Postman เลย เพราะรวม design + test ในตัว (แต่ config เยอะ เป็นเรื่อง implement มากกว่า)
- สรุป: เนื่องจากทีมใช้ Postman อยู่แล้ว ให้ทำต่อบน Postman ได้ ไม่ต้องยึดมาตรฐานตายตัว เพราะไม่ได้ส่งมอบเอกสารให้บริษัทตรวจสอบภายนอก

### 2. บทบาท BA ในการรีวิว API
- BA ไม่ต้องอ่าน code/body ที่อ่านยาก แต่ดูส่วนหัว (parameter, input/output, endpoint) เทียบกับความเข้าใจ business
- ใช้ Sequence Diagram ดู flow การทำงานของแต่ละฟังก์ชัน (เช่น Update User Data By ID) ว่ามีขั้นตอนอะไร input/output อะไร
- รายละเอียดเชิงลึกค่อยลงเมื่อผลทดสอบ (expected vs actual) ไม่ตรงกัน
- Test Case (รหัส TC) ครอบคลุมทั้ง Front-end (UI test) และ Back-end (API test) อยู่แล้ว — ใช้เป็นเอกสารทดสอบหลัก ไม่ต้องแยกเอกสารเพิ่ม

### 3. UI Design Spec
- ใช้ Figma เป็น UI design spec ได้เลย ไม่ต้องทำเป็นเอกสารมาตรฐานแยก เพราะไม่มีการส่งมอบเอกสารให้บริษัทตรวจสอบ
- เน้นทำ link ให้เชื่อมกัน (PRD ↔ หน้าจอ) เพื่อให้ BA trace back ได้เมื่อเอกสารเยอะขึ้น — ใช้ซอฟต์แวร์ออนไลน์/ดิจิทัลทั้งหมด
- สิ่งที่ส่งมอบให้ลูกค้าเมื่อ request เสร็จ: ฟังก์ชันที่ใช้ได้จริงให้ลองทดสอบ + Test Case + เอกสาร feedback สำหรับแจ้ง bug

### 4. การยืนยัน Requirement (sign-off / acknowledge)
- ที่ปรึกษาเสนอให้เพิ่มส่วนยืนยัน requirement ท้ายเอกสาร โดยให้ลงชื่อทั้ง 2 ฝั่ง (ผู้ Request และฝั่งบริษัท/ทีม) เพื่อยืนยันว่าเข้าใจตรงกันแล้ว
- เหตุผล: ป้องกันปัญหา requirement ไม่ชัด/เข้าใจไม่ตรงกัน ที่เคยทำให้ต้อง burn เวลาแก้งานซ้ำ; ใช้อ้างอิงว่าการเปลี่ยนภายหลังคือ Change Request ไม่ใช่การแก้งานเดิม
- **ประเด็นจากทีม (พี่เกม):** ผู้ให้ requirement เป็นผู้บริหาร การให้เซ็นเป็นทางการอาจดูเกร็ง/"โดนด่า" — ที่ปรึกษาเข้าใจบริบท in-house
- ทางออกที่ยืดหยุ่นกว่า:
  - ไม่ต้องเซ็นทางการ แต่สรุปเป็นภาษาที่อ่านง่าย (MOM สั้น ๆ 1-3 ประโยค) โพสต์ใน chat กลุ่ม/Telegram แล้วให้กด like / heart / confirm หรือตอบ mail ว่า yes เพื่อเป็น acknowledge
  - ตัว PRD ยังเป็น source of truth ของทีม แต่ย่อยเป็นก้อนเล็กเวลาสื่อสารกับผู้บริหาร
  - หลักการคือ Requirement Translation: ทีมต้องสรุปสิ่งที่ผู้บริหารพูด (ก้อนใหญ่ → break down เป็นฟังก์ชันย่อย) แล้วยืนยันความเข้าใจกลับไป
- ใช้หลักฐานนี้อ้างอิงเรื่อง timeline / การเข้าคิวงาน / การต่อรองเวลาได้

### 5. เอกสารย้อนหลังสำหรับซอฟต์แวร์ที่มีอยู่แล้ว
- ไม่จำเป็นต้องสร้างเอกสารทั้งหมดตั้งแต่แรก
- สำหรับซอฟต์แวร์ที่ยัง live/patch ต่อเนื่อง (2-3 ปี): ไม่ต้องทำ requirement ย้อนหลัง แต่ให้ AI ช่วย list ฟังก์ชันทั้งหมดว่ามีอะไรบ้าง แล้วรีวิว
- เป้าหมาย: มี "แผนที่" ฟังก์ชัน + เช็คว่าแต่ละฟังก์ชันมี Test Case หรือยัง ค่อย ๆ เติม เพื่อกันปัญหา use case ใหม่ชนของเก่า (domino effect)
- กรณี fork: ถ้า App B fork จาก App A จริง ๆ ให้อ้างอิงเอกสาร A ได้เลย ไม่ต้อง generate B ใหม่ทั้งหมด แค่ระบุส่วนที่ + เพิ่มเข้ามา (A + ΔB)

### 6. โปรเจกต์ใหม่ OMBED (Wallet ตัวใหม่)
- Wallet ตัวเก่ามีปัญหา จะสร้าง Wallet ใหม่มาแทน (Replacement) โดยใช้แนวคิด Wallet เดิม + extend use case
- โปรเจกต์นี้ชื่อ OMBED — เป็นโปรเจกต์ใหญ่ รวม Wallet + หน้า auto (ฝั่งพี่ตุ่มดูแล) + โปรแกรมอื่นที่ต่อเข้ามา; scope ของ Wallet จะกลายเป็นทั้งโปรเจกต์ OMBED
- งานเอกสารที่ทีม BA ทำมาทั้งหมดจะเอามาปรับใช้กับ OMBED
- **Tech stack / infra:**
  - CI/CD: ใช้ GitHub Actions เป็นหลัก (ต่างจาก 1BX), build เป็น Docker image ทั้ง front และ back
  - Database: PostgreSQL (เลือกเพราะ extension เช่น TimescaleDB สำหรับ time-series/aggregation และรองรับ sharding, ยืดหยุ่น) — traffic Wallet สูงแต่ที่ปรึกษาเห็นว่าไม่ติด
  - Migration: ย้ายข้อมูล Wallet เก่า (MySQL) → ใหม่ (PostgreSQL)
