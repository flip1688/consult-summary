## เนื้อหาสำคัญ

### วัตถุประสงค์ของระบบ
- อยากได้ "หัวสมองกลาง" ที่รวบรวมความรู้ทั้งองค์กร: source code, เอกสาร, transcript/A-script การประชุม, Figma, ClickUp ฯลฯ
- แก้ปัญหาความรู้กระจุกอยู่ที่คนคนเดียว — เวลาคนไม่อยู่ (เช่น ลาไปเที่ยว) คนอื่นต่องานไม่ติด; ให้ AI ตอบได้ว่าโปรเจกต์ไปถึงไหนแล้ว
- ระบบต้องรองรับการถามด้วย "ภาษาไทย" (mix กับอังกฤษ) และเก็บข้อมูลไว้ภายในองค์กร (Local/Private ไม่ส่งออกข้างนอก)
- เป็นการให้น้องๆ ทุกสายงาน (รวมถึง BA, Designer) เข้าใจพื้นฐานการสร้างระบบนี้เพื่อต่อยอดได้เอง

### สถาปัตยกรรม RAG — 5 กระบวนการ
1. **Ingest** — ดึงข้อมูลจากแหล่งต่างๆ (Google Drive กลาง / dedicated folder, source code, PDF, Word, JSON, Markdown)
2. **Embed** — แปลงข้อความเป็นเวกเตอร์ (ตัวเลข), ทำ chunking
3. **Store** — เก็บใน MongoDB + File System พร้อม vector index
4. **Retrieve** — ค้นข้อมูลผ่าน Retrieval API (vector/similarity search)
5. **Generate** — LLM ปั้นคำตอบเป็นประโยคภาษาไทย/อังกฤษที่อ่านง่าย

### Tech Stack ที่เสนอ
- **Infra:** Google Cloud + **Cloud Run** (serverless, scale-to-zero ไม่มี request = ไม่เสียเงิน, คิดแบบ consumption)
- **Backend/Framework:** Python + **LangChain**, FastAPI
- **Database:** **MongoDB (Atlas v8)** — ใช้ **Hybrid Search** (เพิ่ง GA), vector search, rank fusion
- **Embedding model:** โมเดลของ MongoDB (ถอดเสียงว่า "Context 4" — น่าจะเป็น Voyage embedding ที่ผูกกับ Mongo)
- **LLM:** Local/Open-source model ผ่าน GCP (พูดถึง **Gemma**, **Qwen**, **Typhoon/ไทคูน** ของ SCB สำหรับภาษาไทย) หรือใช้ **Vertex AI**
- **Observability:** Cloud Logging/Monitoring; ทางเลือกเสริม LangSmith / LangGraph (ตัวฟรี)
- **Security by design:** GCP Secret Manager + IAM/RBAC

### ACL / RBAC (Access Control List)
- กรองข้อมูลตาม role/แผนก/โปรเจกต์ของผู้ล็อกอิน เพื่อให้คำตอบตรงประเด็น, index แคบลง (เร็วขึ้น), และปลอดภัย (ดีกว่าเอาไฟล์ md ไปกองที่เดียวที่ทุกคนเห็นหมด)
- แนะนำทำเป็น **Role-Based (RBAC)** เพราะขยายง่ายเมื่อองค์กรโต; MongoDB ออกแบบรองรับได้
- ช่วยลด token/เวลาในการถาม-ตอบ (ไม่ต้อง search กว้างทั้ง 10 โปรเจกต์)

### แนวคิดพื้นฐานที่อธิบายน้องๆ
- Embedding = แปลงข้อความเป็นชุดตัวเลข (token) ให้คอมพิวเตอร์เข้าใจ; ภาษาไทยใช้ token เยอะกว่าปกติ
- Vector/Similarity search = หา "ความใกล้เคียง" ไม่ใช่ค้นเป๊ะ (ยกตัวอย่างค้นรูป Apple → คืนผลใกล้เคียงเรียงอันดับ)

### Chunking / ขนาดข้อมูล
- MongoDB document < 16MB; 1 chunk ~= 1,000 token
- ออกแบบให้รองรับได้ถึง ~1 ล้าน chunk ต่อ index
- source code (ที่ coding agent มักแตกเป็นหลายไฟล์เล็กๆ) embed ได้ทั้งไฟล์; Markdown สกัดได้ทั้งหมด
- **PDF ไฟล์ใหญ่:** ไม่จำเป็นต้องใส่ทั้งหมด — ควรทำ summary ก่อน (เสนอสร้าง "skill" ใน Coding Agent ให้สรุป PDF ก่อน ingest) แล้วค่อยดึง detail จากไฟล์จริงทีหลัง
- ประเมินขนาด: เช่น Google Drive กลาง ~1TB เข้า Mongo อาจเหลือ ~700GB (หด ~30%)
- **Ingest 2 แบบ:** 1-time (ครั้งแรก) + Incremental (มี monitor คอย update เมื่อ push code ใหม่ขึ้น GitHub)

### Agent Memory (หัวใจของการออกแบบ)
- **Short-term:** context window ต่อ session/user, ทำ checkpoint ให้คุยต่อได้เมื่อสายหลุด/กลับมาใหม่, เก็บชั่วคราว (เช่น 7 session ล่าสุด, ใช้ TTL index ลบทิ้ง)
- **Long-term:** แบ่งเป็น Procedural / Episodic / Semantic — เก็บใน Knowledge Base ทำให้ระบบฉลาดขึ้นเรื่อยๆ (ถามซ้ำเรื่องเดิมตอบได้เลย เหมือน expert)
- **Semantic Cache:** เก็บคำตอบที่ LLM ปั้นไว้เป็น vector; ถ้าถามคล้ายเดิมก็ตอบจาก cache ทันที ไม่ต้องเรียก LLM ซ้ำ → ประหยัด token + response time เร็วขึ้น (คล้าย Redis)

### Agentic System
- มีหลาย agent เฉพาะทาง (เช่น research / coding / infra agent) + ตัว orchestration/front agent ตรงกลางคอยตัดสินว่าใครทำอะไร ส่งต่อให้ใคร
- พยายามแปลงจาก non-deterministic → deterministic ให้มากที่สุด; ลดการเสีย token แต่ใช้ข้อมูลจริงมากที่สุด

### รีวิวแพลนของคุณบี
- คุณบีส่งแพลน (อยู่เฟส Planning) มาให้รีวิว; พี่ฟี่ใช้ AI ช่วยรีวิวแต่ย้ำว่าเชื่อ AI ทั้งหมดไม่ได้
- ผลรีวิว: **โดยรวม Architecture/แพลน OK, ไม่มี critical blocker จริง**
- ประเด็นที่ AI จับ (สีแดง) ส่วนใหญ่ไม่ใช่ปัญหาจริง เช่น บาง function มีอยู่แล้วใน Atlas (ตัดทิ้ง), เรื่อง dimension "ผิด" จริงๆ ได้ถึง 4 แบบ ไม่ใช่ประเด็น
- ควรใช้ **Hybrid Search** (มีทั้ง text search + vector search / rank fusion)
