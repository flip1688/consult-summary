### รีวิว ER Diagram ระบบ Wallet เก่า (dbdiagram)
- โครงสร้างใหญ่พอสมควร — 1 user มีหลาย Wallet, 1 user มีหลาย Wallet Transaction
- **ข้อสังเกตสำคัญของพี่ฟี่:** ในตาราง Wallet Transaction **ไม่เห็นฟิลด์ Wallet ID** — ถ้าอยากรู้ตรงๆ ว่า transaction นี้มาจากกระเป๋าไหนจะรู้ไม่ได้ (ต้องวิ่งผ่าน User เสมอ) ทั้งที่ 1 กระเป๋าควรมีได้หลาย transaction; ส่งผลต่อการ compare/ตรวจ Balance กับ Initial Credit ด้วย
  - ทีมรับไปตรวจสอบ (คุณโดนัทเช็คจากหน้า UI: ต้องกรอก User ID/Member ก่อนถึงจะเห็น transaction)
- ตั้งข้อสังเกต naming convention: `member_id` เป็น varchar(255) ใน User — 1 user สร้างได้หลาย member หรือไม่
- ส่วน Permission (User/Permission List/ผู้ช่วย/Admin), Config Game/Product ต่างๆ มี pattern ชัดเจน — โดยรวมโอเค

### แผน Migration MySQL/MariaDB → PostgreSQL (My Gate — พี่เบ้น)
- **Steps มาตรฐาน:** Assess spec → Convert → Migrate → Validate → Cutover
- **เครื่องมือ:** AWS **DMS** (มี CDC ในตัว ทำ continuous migration ได้จน app พร้อม switch) + Schema Conversion Tool ของ AWS สำหรับแปลง schema/Stored Procedure/View; DMS ของ AWS ใช้ง่ายกว่าของ GCP มาก (บีลองของ GCP แล้วไม่สำเร็จ) และใช้ข้าม cloud ได้
- **โจทย์ที่คุยกันหนัก — อยากรัน 2 ระบบคู่ขนานให้ลูกค้าเลือกใช้:**
  - Sync 2 ทาง (bidirectional) ระหว่าง DB คนละประเภท **เสี่ยงระบบพังมาก ไม่แนะนำ** (conflict ของ data)
  - ท่าที่ปลอดภัย: ให้ **MySQL เป็นตัวเขียน (write) ฝั่งเดียว**, PostgreSQL/ระบบใหม่เป็นตัวอ่าน (read) ให้ลูกค้าลอง UX ใหม่
  - โครงสร้างเก็บข้อมูล 2 ระบบไม่เหมือนกัน (เช่น user config vs จัดเป็น group) → ถ้าจะให้ smooth จริงต้องทำ **Adapter** ตรงกลาง (ให้ AI ช่วย gen/review code ได้)
  - แผน cutover: ปิด UI เก่า (DB ยัง sync) ให้ลูกค้าคุ้น UX ใหม่ก่อน → รอ **lag = 0** (ไม่มี transaction ไหล) ช่วง traffic ต่ำ → switch endpoint; เลือกได้ระหว่างประกาศปิดปรับปรุงสั้นๆ กับ switch ทันทีแล้ว dump data ที่ค้างตามไป (แนะนำปิดสั้นๆ เพื่อ **Validate ข้อมูลก่อน switch ถาวร**)
- **ข้อควรระวัง / ต้อง Simulate ก่อน:**
  - ปลายทางที่มี extension เช่น **TimescaleDB Hypertable** — DMS ไม่สร้างให้ ต้อง create เองก่อนแล้วค่อย transfer data (ต้องเทสต์)
  - **MariaDB** รองรับใน DMS ที่ version 10+ — ระบบเก่ามีทั้ง MySQL และ MariaDB ต้องเช็ค compatibility (พี่โดเคยเจอปัญหา engine ตอนย้าย MariaDB → MySQL)
  - **Index / Foreign Key:** DMS ไม่ transfer index ให้ครบ — แนะนำ export index จาก MySQL มา convert เป็น pattern ของ PostgreSQL แยกต่างหาก และ **full load ข้อมูลก่อนโดยยังไม่ใส่ index** (ใส่แล้วช้า) พอเข้าโหมด CDC ค่อยทยอย apply
  - ข้อมูลขนาดใหญ่ (หลาย TB — เคยแค่ restart เครื่องยังใช้ 2 วัน): ปรับสเปค instance ปลายทางสูงๆ ช่วง full load แล้วค่อยลดลง
  - **Validate:** นับจำนวน record ทุก table + sum ยอดเงิน (ประสบการณ์พี่โด: จำนวน record อย่างเดียวไม่พอ เคยเจอข้อมูลขาดจริง)
  - **ไฟล์ใน S3 → GCS:** ใช้ tool ย้าย bucket แล้ว remap URL ใน table (ถ้าเก็บเป็น public URL ของ CDN ให้ replace โดเมน/prefix ได้เลย — ให้ AI เขียนสคริปต์ทำได้, ทำเป็นขั้นตอนหลังย้าย data เสร็จ)
- **เริ่มลงมือ:** Setup MySQL + PostgreSQL, export structure ทุก table + สุ่มข้อมูล (~10 record/table) แล้วลองรัน DMS ดูว่าอะไรรอด/ไม่รอด จะได้เห็นโจทย์ว่าต้อง custom ตรงไหน
