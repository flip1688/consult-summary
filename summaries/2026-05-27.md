## เนื้อหาสำคัญ

### นิยาม TPS และองค์ประกอบ
- TPS = จำนวน transaction ที่จบครบ loop ตั้งแต่ Front-end → Back-end → Database และกลับออกมา ภายใน 1 วินาที
- Baseline ความช้าของ query อยู่ที่ 100 ms — ถ้า query/insert เกิน 100 ms MongoDB จะ mark เป็น slowness และ Performance Advisor จะแนะนำวิธีแก้ (เช่น เพิ่ม index)
- แนะนำให้ใส่ค่า App Name ใน connection ของแอป เพื่อให้รู้ว่า slow query มาจาก service ตัวไหน
- 1 TPS ประกอบด้วย:
  - **RPS (Request Per Sec):** คนเข้ามาที่หน้าเว็บ/เปิดค้างไว้ ดูรายการเกม แต่ยังไม่ actio(view-only) — ปริมาณอาจสูงมากแต่ไม่แตะ DB
  - **QPS (Query Per Sec):** activity ที่ยิงเข้า DB จริง (login, เช็คเงิน, ลงเกม, ดึง ticket, บันทึกผลแพ้ชนะ)
- โดยทั่วไป QPS จะเยอะกว่า RPS เพราะ 1 request/action อาจก่อให้เกิดหลาย query เช่น การเบ็ตเกม 1 ครั้งอาจ connect DB ~5 ขั้นตอน ดังนั้นถ้ามีผู้ใช้ 4,000 คน DB อาจต้องรองรับราว 9,000+ QPS (จำนวน action × ผู้ใช้)

### การ Scale ฝั่งหน้าและ Cache
- ฝั่ง Front-end/API scale แบบ Horizontal (copy pod เพิ่ม) ต้องเช็คว่า Load Balancer รองรับได้แค่ไหน แล้วดูว่าคอขวดไปตกที่จุดใด
- ใช้ Cache (Redis เป็น default ที่ทุกลูกค้าใช้) กับข้อมูลที่ไม่ใช่ real-time / ไม่เกี่ยวกับเงิน (เช่น list รายการเกม) เพื่อลดภาระ DB — งานที่ต้องแตะ DB จริง (ตัดเงิน Wallet) ต้องยิงตรงถึง DB

### คอขวดและการ Scale ของ MongoDB
- Bottleneck ส่วนใหญ่ที่เจอคือ Database (ฝั่ง pod ดู metric ของ Kubernetes ได้ง่ายกว่า)
- **1 connection ≈ 1 MB RAM ของ MongoDB**
- `maxPoolSize` (ในทรานสคริปต์เพี้ยนเป็น "Mac WhoSite") ค่า default = 100 → 1 API request อาจแตกเป็นได้ถึง 100 connection = ~100 MB
- เมื่อ scale pod เช่น 10 pod → 10 × 100 = 1,000 connection ≈ 1 GB RAM แม้ใช้งานจริงไม่ถึงขนาดนั้น จึงควรปรับ maxPoolSize ให้พอเหมาะกับ memory
- การ scale tier: M10 → M30 → M80 → M200; ตัวอย่าง M30 มี RAM ~64 GB โดย MongoDB (WiredTiger) reserve ราวครึ่งหนึ่ง (~30.5–32 GB) เป็น cache ที่ดีที่สุด ส่วนที่เหลือแชร์กับ OS
- เมื่อ RAM ถูกใช้จนเกินโซนปลอดภัย (เขียว→แดง) จะกระทบ CPU และ IO ทำให้ระบบช้าและตอบสนองผู้ใช้ไม่ได้ = สัญญาณว่า spec เริ่มไม่เหมาะกับโหลด

### เครื่องมือ Load Test
- **K6** ("เคซิก/Classic"): ทำ integration test End-to-End จากหน้าบ้านถึงหลังบ้าน ลูกค้าใช้อยู่แล้ว ดูค่า P90/P95/P99 ได้
- **Locust** ("ลูคัส/Lucrast"): เครื่องมือ performance test ที่ยิงตรงไปที่ MongoDB (MongoDB แนะนำ) generate/random data แล้วยิง insert/update/delete เพื่อวัดว่า DB tier (เช่น M30) รองรับได้กี่ QPS สูงสุด — ช่วยตัดสินใจว่าควรเริ่มที่ M เท่าไหร่
- Locust generate user จาก worker ของตัวเองได้เยอะกว่า K6 บนเครื่องปกติ

### การตอบผู้บริหาร (รองรับผู้ใช้ได้กี่คน)
- ไม่ตอบจำนวนคนตรงๆ แต่ตั้งสมมติฐานจาก activity จริง เช่น 1 ผู้ใช้เล่นพร้อมกัน 3–4 เกมต่อวินาที แล้ว load test ยิงพร้อมกันตาม scenario นั้น
- เชิง Engineering ต้องดูค่าเฉลี่ย latency ต่อ 1 รอบ (300/500 ms) เพื่อรู้ว่าคอขวดอยู่ที่ DB / API / Load Balancer เพื่อไปแก้ให้ถูกจุด
- **1 scenario = 1 transaction = 1 TPS** (เช่น login → ดูรายการ → รับ token → แทง รวมเป็น 1 scenario)

### ปัญหาที่พบ
- ทีมของคุณบี simulate V user ได้แค่ ~350–1,000 จากเครื่องเดียว (ติด limit CPU/core ของเครื่อง) ยังไม่สามารถทดสอบระดับหมื่น/แสนได้ — ต้องหาแนวทาง distributed/cluster หรือใช้ test machine / cloud computing (เดิมเคยใช้วิธีให้คนหลายคนกดยิงพร้อมกัน ซึ่งจำกัดตามจำนวนเครื่อง)
