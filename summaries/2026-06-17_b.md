## เนื้อหาสำคัญ

### 1. Multi-Document Transaction — Atomic (สำเร็จทั้งหมด หรือ rollback ทั้งหมด)
- ยืนยันหลักการ: ถ้าใช้ transaction ทุกกิจกรรมใน scope ต้องสำเร็จพร้อมกัน ("ไปพร้อมกัน เสียพร้อมกัน") — ถ้าไม่ commit ทุกอย่างต้อง rollback หมดโดยธรรมชาติ
- แนะนำให้เขียน logic เน้นว่า **ทุก step ต้องผ่านถึงจะ commit; ถ้าไม่ใช่ commit → rollback ทั้งหมด** เพื่อกันการเล่นลอด commit โดยไม่ตั้งใจ
- **คำถามคุณบี:** เคส record แบบ set (เช่น XQ เปิดออเดอร์ครั้งแรก แล้วมี call ด้านนอก แบบ pattern พี่โด) — ถ้า call fail แล้วต้องกลับมา update status ว่า fail ถือเป็นการทำซ้ำซ้อน (update ในช่วงเวลาสั้นๆ) ไหม?
  - **คำตอบ:** การทำเป็น single action (transaction) ดีกว่าการ insert แล้วค่อยกลับมา update status เอง — เพราะ manual update status = ต้อง lock/แก้ record เดิมซ้ำ ยุ่งกว่า ในกรอบ transaction เราแค่คาดหวังว่ากิจกรรมทั้งหมดสำเร็จ ถ้า call ไม่ผ่านก็ rollback ทั้งชุด (record เดิม, collection เดิม)

### 2. หลีกเลี่ยง Long-running Job / Batch update ก้อนใหญ่ — ให้ซอยงาน (Chunking)
- ประเด็นนี้ **ไม่ใช่เรื่อง Begin/End transaction** แต่เป็นเรื่องงานที่ประมวลผลข้อมูลก้อนใหญ่มาก (หลักล้าน–พันล้าน record) ไม่ควรทำรวดเดียว เพราะจะกิน memory / รัน transaction ยาวเกินไป
- **วิธี:** ซอยเป็นชุดย่อย (batch processing) — เช่นงาน DELETE ข้อมูลเก่ากว่า 30 วันบน data ~1 billion:
  - อย่ารัน `DELETE` ทีเดียวทั้งก้อน → ทยอยลบทีละวัน; ถ้าวันเดียวยังใหญ่ (~100M) ก็ซอยย่อยลงอีก เช่นทีละ 10 ชั่วโมง แล้วทยอยลบทีละ 5 นาที
- **เคสลูกค้าจริง:** มี ~500k คลิก/วัน ต้องการเก็บแค่วันเดียว จึงต้องลบทุกวัน แต่ลบให้หมดใน 24 ชม. ด้วยคำสั่งเดียวไม่ทัน
  - ต้องคำนวณ speed การลบให้ทันและ **ไม่กระทบ operation ปกติ**
  - **ห้ามให้ job รันชนช่วง peak** (เย็น ~18:00 ถึงตี 1 ที่คนเข้ามาเล่นเยอะ) เพราะจะทำให้ระบบช้า/พัง → จัดเวลา/ซอยให้เลี่ยงช่วงนั้น

### 3. Connection Pooling & maxPoolSize
- **maxPoolSize default = 100** ต่อ 1 connection/instance ถ้าไม่ตั้งค่าอะไร — จองไว้ ~100MB ต่อ connection (กิน RAM)
- 1 API/service ที่ connect ไปแล้วจะเปิด pool active ~100 ไว้ reuse; request ที่เข้ามาถ้ายังมี connection idle ในพูลก็ใช้ต่อได้ทันที (ไม่เปิดใหม่)
- เมื่อ concurrency ยิงเข้ามาจนใช้ครบ 100 (idle = 0) แล้วมี request เพิ่ม → ต้องเปิด connection ใหม่ ซึ่งมี overhead (authentication / handshake / SSL) ทำให้ช้าในจังหวะนั้น (เปรียบเหมือนสร้างถนนเลนใหม่)
- **Anti-pattern ที่ต้องเลี่ยง:** เปิด connection ใหม่ทุกครั้งที่ call — ต้อง **reuse connection**
- **การจูน:** ไม่ต้องแตะถ้าใช้ default 100 พอ; ให้ดู metric บน Atlas ว่าใช้จริงเท่าไหร่ แล้ว base on:
  - service นั้น call DB นานแค่ไหน (ms/sec) และ concurrency จริงเข้ามาพร้อมกันเท่าไหร่
  - API ที่คนใช้ไม่บ่อย + query จบเร็ว (เช่น login select where) → concurrency จริงอาจแค่ ~10 ไม่ถึง 100 → **ลด pool size** เพื่อประหยัด RAM (10 API × 100 = ~1GB)
  - API ที่ถูกเรียกถี่ + operation ใช้เวลานาน (เช่น update Wallet / คำนวณซับซ้อน) → 100 อาจไม่พอ → **เพิ่ม pool size**
  - เอา RAM ที่ประหยัดจากเส้นที่ใช้น้อยไปเพิ่มให้เส้นที่ใช้หนักได้

### 4. Diagnosis / Monitoring
- **Heuristic:** ถ้า RAM (Lamp) พุ่งสูงแต่ CPU แทบไม่ขึ้น → แปลว่า **จอง connection ไว้สูงเกินไป / เปิด connection ทิ้งไว้เยอะแต่ใช้จริงน้อย** (pool ใหญ่เกิน)
  - เคสจริง: ลูกค้ามี 10 API / 10 pod แต่เปิดถึง ~8000 connection ขณะที่ CPU แทบไม่ขึ้น = เยอะเกินไป
- ถ้าตั้ง pool **ต่ำเกินไป** → จะเห็น slowness ที่ CPU/Network (ต้อง handshake/SSL ใหม่บ่อย) ผู้ใช้จะรู้สึกช้าเป็นช่วงๆ
- **M-Tier cap:** connection มี maximum ตาม tier ของ Atlas — scale pod เพิ่ม (20/30/100 pod) จะไปตันที่ max connection ของ tier นั้น; tier ต่ำ = connection น้อย
- **สรุปงานที่ควรทำ:** เซ็ต alert monitoring, ดู profiler และรีวิว recommendation ที่ระบบแนะนำ เพื่อเอาไปวิเคราะห์/แก้ปัญหา

### 5. รีวิว Index ของโปรเจกต์คุณบี (ช่วงท้าย)
- พี่ฟี่ดูโครงสร้าง (structure) แล้วมองว่า **structure โอเค ไม่ติดปัญหา** แต่ต้อง **รีวิว index อย่างละเอียด** เพิ่ม
- สอบถามว่าโปรเจกต์มี test/structure และ **load test environment** ไหม → คุณบียืนยันว่ามี **load test** (บนเครื่องตัวเอง / ต้องสร้างเครื่องขึ้นมาโหลดข้อมูล)
- **แผน:** พี่ฟี่จะส่ง command / script (แนว explain — "charge key analysis" = execution plan analyze) ไปให้รันบนเครื่องที่ทำ load test เพื่อ analyze index ก่อน — เป็นการดูเบื้องต้นก่อนจะตัดสินใจไปวิเคราะห์บน production จริง

## การตัดสินใจ / ข้อตกลง
- เคส insert + external call: ใช้ **single/transaction (atomic)** ดีกว่า insert แล้วกลับมา update status เองภายหลัง
- งานประมวลผล/ลบข้อมูลก้อนใหญ่: ให้ **ซอยเป็น batch** และจัดเวลาเลี่ยงช่วง peak เสมอ
- Connection pool: ใช้ default 100 ได้ถ้าพอ; จูนขึ้น/ลงราย service ตาม concurrency จริง + ระยะเวลา call โดยดูจาก metric
- ต้องเซ็ต alert monitoring + ใช้ profiler/recommendation เป็นเครื่องมือวินิจฉัย
- โปรเจกต์คุณบี: structure ผ่าน แต่จะทำ **index analysis บน load test environment** ก่อน (ยังไม่แตะ production)
- หัวข้อ "เรื่องชาติ" ของพี่ฟี่ยกไปคุยวันหลัง; ปิด meeting เพราะหมดเวลา
