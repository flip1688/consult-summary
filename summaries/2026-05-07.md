## เนื้อหาสำคัญ

### Networking และ Infrastructure
- ใช้รูปแบบ Hub-and-Spoke VPC บน GCP: Hub VPC เป็นหน้าด่านคุม Firewall/central networking, Spoke แยกเป็น Production / Staging
- เชื่อมต่อไปยัง AWS (ซึ่งโฮสต์ระบบ Wallet) ผ่าน VPN site-to-site (Private Connection)
- ระบบธุรกิจแบ่งเป็นโซน: **Wallet** (เก็บข้อมูลผู้เล่น/Agent, คุมการเล่นและเชื่อมต่อเกม — ยังอยู่ AWS) และ **Autofast/Autofund** (ระบบปากทอน/จัดการ Promotion — อยู่ GCP). Autofast ต้อง cross-site ไปเรียก Wallet บน AWS จึงเกิด latency; มีแนวโน้มอยากย้ายมาแพลตฟอร์มเดียวกัน แต่ยังไม่กำหนดเวลาเพราะระบบ live ตลอด

### GKE / Cluster
- รันบน GKE, ใช้ single cluster ต่อ business unit แล้วเชื่อมกันผ่าน **Fleet** (เช่น cluster Autofund กับ cluster Payment Service คุยกันผ่าน Fleet)
- แยก cluster ตาม Business Unit เพื่อจัดการต้นทุน (รู้ cost ต่อ BU ชัดเจน) และเพื่อ fault isolation

### Service Communication
- Microservices อยู่ใน cluster เดียวกัน
- แบบที่ 1 (ใช้อยู่ตอนนี้): เปิด endpoint เดียว (เช่น port 80) เข้าได้ทั้งจาก internet และภายใน cluster โดย verify ด้วย JWT / API Key
- แบบที่ 2 (กำลังพิจารณา): มี API Gateway/Aggregation service คั่นกลาง internet เรียก service ตรงไม่ได้ ต้องผ่าน API ที่ aggregate ข้อมูลจาก service ต่างๆ ก่อน
- ยังไม่ตัดสินใจว่าจะใช้แบบไหน และจะใช้เทคโนโลยีอะไร (GraphQL / service call) ขึ้นกับภาษาที่คนดูแลถนัด

### ภาษา / Tech Stack
- มี 3 ภาษา: **C#** (.NET เวอร์ชัน 10 — ทีมหลัก 1BX), **PHP** (Laravel 8.1 และ 8.3 — Autofast), **Go** (เวอร์ชัน 2 ขึ้นไป)
- เหตุผลที่หลายภาษา: แต่ละทีมถนัดต่างกัน และโปรเจกต์ที่รับมามักถูกค่อยๆ rewrite เป็นภาษาที่คนดูแลถนัด
- ทีมชอบ C# เพราะโครงสร้าง/contract ชัด compile-time ช่วยคุมคุณภาพเมื่อมี dev หลายระดับ
- P'Fee ให้ความเห็นว่า อุตสาหกรรมนี้ (จากประสบการณ์) มักใช้ Go/Node เยอะเพราะ Go deploy แล้ว memory ต่ำ, binary เล็ก, scale ดี — ส่วนตัวโน้มเอียงไป Go และอยากให้รวมเหลือ 1-2 ภาษาโดยเน้น performance แล้วใช้ AI Agent ช่วยตรวจคุณภาพ (Go ทำ unit/integration/contract test ได้เหมือนกัน แต่ style ทางการน้อยกว่า C#)

### CI/CD และ Source Control
- Monorepo (แต่ละ service อยู่ repo เดียวกัน) บน GitHub
- ใช้ **ArgoCD** + **Config Sync** (Kubernetes/GKE) + **Kustomize** (base + overlays; ArgoCD และ Config Sync มาดู folder overlay) — สอดคล้องรูปแบบ GitOps
- Dependabot: เห็นแล้วแต่ไม่แน่ใจว่า apply ครบทุก repo/org หรือยัง
- **ยังไม่มี Secrets Management** — ปัจจุบัน ENV/connection string ของ production เก็บเป็นไฟล์ property ใน Git (ArgoCD/GitHub) แบบ plaintext, ไม่ได้ทำ hidden/GitHub Secret; Dependabot ก็ไม่เตือนเรื่องนี้

### Testing / Quality
- Unit test: ช่วงแรกของ repo มีเขียนบ้าง แต่หลังๆ ไม่มี และ test ไม่ผ่านก็ commit ได้
- ไม่มี automated/regression test — พึ่งคนเป็นหลัก (โปรแกรมเมอร์เทสเอง → BA/ทีม QA (เช่น OneBX) → go live) พึ่ง compiler/IDE คุม compile-time เท่านั้น, runtime ไม่มี
- ไม่มี pre-commit hook (เคยลองแต่ไม่ได้ใช้จริง)
- P'Fee แนะนำแนวทาง automated test เช่น Playwright (ในถอดเสียงคือ "PayRite") ที่บันทึก flow ไว้ให้รันซ้ำ, และแนวคิดใช้ AI/MCP agent เขียน prompt/skill ให้ dev ระบุว่าต้อง test อะไรแล้วให้ AI produce test (แต่ยอมรับว่าเรื่อง token cost เป็นอีกประเด็น)

### MongoDB Atlas Security Checklist (P'Fee นำเสนอ)
- ปัจจุบัน login Atlas ใช้ database user (username/password) — แนะนำใช้ **OIDC** ผูกกับ IAM กลาง (GCP/AWS) เพื่อคุมสิทธิ์เข้า UI/cluster
- **RBAC/Custom Role ต่อ microservice:** 1 API/microservice ควรมีสิทธิ์เฉพาะ database ของตัวเอง (ทีมยืนยันว่า 1 service = 1 database, 1 user เข้าได้ — น่าจะทำอยู่แล้ว แต่ยังเห็นทุก table ใน db นั้น)
- ใช้ **Private Endpoint** (secure กว่า VPC Peering), ล็อกด้วย IP ผ่าน VPN
- TLS by default (มีอยู่แล้ว)
- **Encryption at rest ด้วย key ของตัวเอง** (BYOK, เก็บ key ที่ Google Secret Manager) เพื่อป้องกันการอ่าน database file แม้เจาะเข้าระบบได้
- **Termination Protection** ป้องกันลบ cluster โดยไม่ตั้งใจ
- **Field-level encryption** สำหรับข้อมูลอ่อนไหว (เลขบัตรประชาชน/บัตรเครดิต)
- **Log export** ไปเก็บที่ระบบกลาง/Data Lake เพื่อ monitoring (ปัจจุบันดู log ผ่าน application อย่างเดียว ไม่เคยดู log MongoDB); ทางเลือกอีกแบบคือ deploy MongoDB operator/control plane บน GKE เพื่อจัดการผ่าน YAML

### Monitoring / Deployment
- Monitoring ใช้ Google Cloud Monitoring (console) อย่างเดียว ไม่มี Prometheus/Grafana แยก
- Deployment ไม่ใช้ Terraform — สร้าง cluster และ setup CI/CD เอง (provision น้อย)
- IP access control + rate limiting ทำที่ Load Balancer ด้วย **Cloud Armor** (เช็ค IP ก่อน แล้วค่อยเข้าไป verify API Key/JWT หลังบ้าน)
- JWT มีตั้ง expiry/refresh, มี IP Access List

### Pentest
- ระบบขึ้น production แล้วแต่ไม่เคยตรวจ (pentest) เลย
- สนใจใช้มาตรฐาน/tool เช่น OWASP (ในถอดเสียง "OVAS/OWASC") เน้น front-end/UI, scan บน staging URL (มี staging environment แยกจาก production เป็น URL จริง)
- แบ่งเป็น 2 phase: (1) scan หาช่องโหว่ที่ image/library ตอน build ก่อน deploy, (2) scan แบบเป็น user เจาะ staging แล้วดู score ว่าผ่านเกณฑ์ไหม
- ยังไม่ต้องถึงระดับ third-party pentest — เริ่มจากมี software ช่วย scan ตามมาตรฐานก่อน
