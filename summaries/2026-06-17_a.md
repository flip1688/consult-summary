### 3. MongoDB Best Practices / Anti-patterns (เนื้อหาหลัก)
รายการสิ่งที่ dev ควร **avoid**:

1. **ลดการใช้ `$lookup`** ให้น้อยที่สุด เพื่อ performance ของ query
2. **หลีกเลี่ยง array ที่โตไม่จำกัด** (embedded array ที่ growth ไม่หยุด — ย้ำจากรอบก่อน)
3. **เก็บ date เป็น BSON date (ISODate) ไม่ใช่ string** — BSON date คือ type ที่เก็บ, ISODate คือ function ที่ช่วยจัดการ
4. **ห้าม mix data type ใน field เดียวกัน** — foreign key ต้องเป็น type เดียวกับ primary key ที่มัน refer (เช่นถ้า `_id` เป็น ObjectID ใน collection A ก็ต้อง cast เป็น ObjectID ใน collection B ด้วย ไม่ใช่เก็บเป็น string) มีผลทั้ง sizing, การใช้ index และ performance ตอน query
5. **อย่าให้ document โตเกิน 16MB** — ห้ามเก็บ binary/ไฟล์ลง MongoDB (trade-off ไม่คุ้ม, ควรใช้ file storage แยก)
6. **อย่ารัน query ที่ไม่มี index บน collection ขนาดใหญ่** — baseline ~1M documents ขึ้นไป โดยเฉพาะ query ที่ถูกเรียกบ่อย
7. **จำนวน index ควร < 20** (max ที่ระบบรับได้คือ 64) — index เยอะเกินไปทำให้ write operation ช้าลง (ต้อง update ทุก index ตอน insert) และเปลือง storage
8. **หลีกเลี่ยง operator ที่ทำให้ index ทำงานไม่เต็มที่:** `$ne`, `$nin` (negation) — ให้ใช้ `$eq`/`$in` แทน; หลีกเลี่ยง `$where`; หลีกเลี่ยง leading wildcard regex (`/^.../`) เพราะ hit index ไม่ได้ — ถ้าจะ search string ให้ใช้ text index / Atlas Search; ควรเช็ค execution plan ก่อน
9. **หลีกเลี่ยง SELECT \* — ระบุเฉพาะ field/column ที่จำเป็นเสมอ** (เรื่อง bandwidth/packet size และ memory ของ database); ถ้าใช้ ORM ให้ทำ model แยกเพื่อดึงเฉพาะ column
10. **หลีกเลี่ยง `skip` สำหรับ pagination บนผลลัพธ์ขนาดใหญ่** — ควรใช้ cursor ทยอยดึง; การนับ total page ให้ใช้ `estimatedDocumentCount` (เร็วแต่ไม่แม่น 100%) หรือรัน count แบบ parallel; `countDocuments` แม่น 100% แต่ช้าเพราะนับทั้งหมด; caching ช่วยได้ (ระบบส่วนใหญ่ผ่าน caching layer อยู่แล้ว)
11. **Aggregation pipeline ที่ซับซ้อนควรเริ่มด้วย `$match` เสมอ** ก่อน `$group`/`$sort`/`$lookup`/`$unwind` — เพราะ `$group`/`$sort` ต้องรอ document ครบทั้ง stage (ไม่ streaming) กิน process เยอะ; `$match` ก่อนช่วยลดจำนวน document ก่อนทำ operation หนัก
12. **กฎ ESR (Equality, Sort, Range) — หลีกเลี่ยง sort ซ้ำซ้อน:** ถ้า index sort ไว้แล้วในทิศทางที่ตรงกับที่ต้องการ ไม่ต้องสั่ง sort อีก (จะกลายเป็น "Sort in Memory" ทั้งที่ index ใน memory เรียงให้แล้ว) — ปล่อยให้ index เรียงตามธรรมชาติเมื่อ direction ตรงกัน
13. **หลีกเลี่ยง index ที่ redundant/unused** — สาเหตุมักมาจาก query pattern ไม่เหมือนกัน (เช่น `{Name, Age}` กับ `{Age, Name}`) เลยสร้าง index หลายตัว; ควร refactor query ให้เป็น pattern เดียวกันเพื่อใช้ index ตัวเดียว (พี่ฟี่เสนอช่วยรีวิว index ที่มีอยู่ให้)
14. **ใช้ Compound Index แทน Single-Field Index หลายตัว** เมื่อ field ถูกใช้ร่วมกันเสมอ (เช่นมี `{Name, Age}` แล้วไม่ต้องสร้าง `Name` เดี่ยวอีก)
15. **การเลือก Shard Key:** ห้ามเลือก field ที่ Low Cardinality (ข้อมูลกระจายตัวน้อย เช่น 1-100) หรือ Monotonically increasing (running number) เพราะแบ่งข้อมูลไม่สมดุล (เช่น Store ID ที่บางร้านมีข้อมูลเยอะกว่ามาก → chunk เอียง) — ควรเลือก field ที่กระจายตัวดี ไม่ซ้ำ เช่น Transaction ID / UUID / ObjectID ที่ split lane ได้เรื่อยๆ เพื่อ balancing
16. **การอ่านจาก Secondary:** อย่าให้ทุกงาน read จาก secondary หมด เสี่ยง Dirty/Stale reads (ข้อมูลยังไม่ sync ทัน) — replica set 3 node (Primary + 2 Secondary) ออกแบบมาเพื่อ **HA ไม่ใช่ scaling**
    - งาน Real-time (เช่นยอด counter ที่ต้องเห็นทันที) → อ่านจาก **Primary**
    - งาน Summary Report ที่ delay ได้ (เช่นสรุปยอดของเมื่อวานหลังเที่ยงคืน) → อ่านจาก Secondary ได้
    - ถ้าต้องทำ analytics/calculation หนักๆ → เปิด **Analytics Node** แยก (เป็น secondary ที่ขึ้นเป็น primary ไม่ได้ จึงไม่กระทบ HA, provision spec/instance ต่างจากกลุ่มหลักได้)
17. **Write Concern / Durability:** เข้าใจ trade-off — `W0` (fire-and-forget เร็วสุด ข้อมูลอาจหาย, แค่ถึง network layer), `W1` (confirm 1 เครื่อง = Primary), `W majority` (default, confirm เกินครึ่ง เช่น 2 จาก 3 → ข้อมูลปลอดภัย) — ตั้งค่าที่ระดับ Connection String; driver รุ่นใหม่ default เป็น majority; เลือกให้เหมาะกับงาน (เช่นข้อมูล log/หลอกที่หายได้ใช้ W1)
18. **หลีกเลี่ยง Multi-Document Transaction ที่ไม่จำเป็น** — ถ้าออกแบบ embed ได้ (เช่น Order embed OrderItem) ให้ทำ embedded model แทนการเปิด transaction คร่อม 2 collection; แต่ยอมรับว่าบางเคสจำเป็นต้องใช้ transaction จริง (เช่น insert transaction + หักยอด/stock, หรือเคส One BX: บันทึกการเดิมพัน + call API operator เพื่อตัดเงิน) — กรณีนี้ควร begin → save → call API → ถ้าสำเร็จ commit / ถ้า fail rollback (ใช้ try/catch ครอบ external API call และ rollback อัตโนมัติเมื่อ error)
