## เนื้อหาสำคัญ

### ช่วงที่ 1 — รีวิว MongoDB / Performance ระบบ 1BX (Wai Production)

- **_id: UUID vs ObjectID** — ปัจจุบัน `_id` ทุกตัว generate เป็น UUID (string ~36–39 ตัวอักษร) จากฝั่ง Application (เดิมตั้งใจทำ prefix แต่สุดท้ายไม่ค่อยได้ใช้). พี่ฟี่แนะนำให้ใช้ MongoDB ObjectID (fix 12 byte) แทน เพราะ:
  - ประหยัด size ของ document และ index (เพราะ `_id` เป็น Primary/Cluster Index by default ทุก collection)
  - ObjectID มี timestamp ฝังในตัว ดึงเป็น Create Date ได้ (ปัจจุบัน 1BX ยังใส่ Create Date เอง ไม่ได้ดึงจาก ObjectID)
- **Optimize document/collection sizing** — ชื่อ field มีผลต่อขนาด document, index (โหลดขึ้น RAM) และ bandwidth. แนวทาง: ในอนาคตถ้าจะ scale ให้เก็บชื่อ field แบบย่อใน DB แล้วทำ enum/mapping ที่ Application (Report/Mapping Layer) แปลความหมายให้อ่านออก — ประหยัดได้ significant มากเมื่อ data โตหลักร้อยกิ๊ก/เทระ (แต่แลกกับความอ่านยาก)
- **Date fields** — เก็บเป็น datetime type อยู่แล้ว (ไม่ได้เก็บเป็น string) ขนาดเหมาะสมกับงานแล้ว ตรวจได้จาก MongoDB Compass
- **Naming convention** — เจอ VET ID จุดเดียวเป็น lowerCamelCase ที่เหลือเป็น UpperCamelCase (เกิดจาก serialize มาจาก C# class) แนะนำให้เป็น pattern เดียวกันเพื่อ manage ง่าย (ไม่มีผลต่อ sizing) — Mongo ไม่มี naming standard ตายตัว ขอแค่ทีมทำให้สอดคล้องกัน
- **Null / empty fields** — MongoDB ไม่จำเป็นต้องใส่ field ที่ไม่มีค่า (ต่างจากการประกาศ null ใน .NET entity) เพราะทำให้ storage โตขึ้น. ที่มีอยู่เป็น debug/meta ที่ยังติดค้าง แนะนำพิจารณาเอาออก (ต้องดู impact ก่อน) และใช้ lib/framework ช่วยจัดการตอน query
- **Unbounded Array** — array ที่ไม่กำหนด limit และถูกทำ index จะทำให้ performance ตอน query ตกเมื่อโตขึ้น (แม้ hard limit 1 document = 16MB). Best practice: จำกัดจำนวน (เช่น 500–1,000) แล้วส่วนเกินแยกไป collection ต่างหาก (เช่น bet IDs, รูปแบบ comment ของ Facebook). Pain point อยู่ที่ Memory ของ Index. ฟิลด์ที่ไม่ได้ index/ไม่ได้ใช้บ่อยแต่ดึงติดตลอด = เปลือง network bandwidth
- **Long string** — string field ค่าเดียวไม่ต้องกังวล/ไม่ต้องแยก ใช้ Atlas Search / full-text search จัดการ index สำหรับ search
- **API Key / Field Level Encryption** — API Key ปัจจุบัน encrypt + มี prefix (~30 ตัว) แต่ยัง sensitive ถ้ามีคนเปิด DB ผ่าน Compass/Shell แล้วอ่านเห็น. พี่ฟี่แนะนำ **CSFLE / Queryable Encryption**:
  - Insert แล้ว encrypt อัตโนมัติ, query ได้โดยไม่ต้องถอดรหัส (QE รองรับ prefix/suffix/substring query)
  - Master Key เก็บที่ **Google KMS**, DEK (Data Encryption Key) เก็บบน MongoDB, ถอดรหัสที่ฝั่ง Application (กัน man-in-the-middle)
  - Compass ต้อง login พิเศษเพื่อดึง key มาอ่าน. ไม่ช้าอย่างมีนัยยะในการใช้งานจริง (ธนาคาร/บัตรเครดิตใช้กันเพื่อ PDPA) — เลือก encrypt เฉพาะ field ที่ sensitive
- **Join / Lookup** — ส่วนใหญ่ไม่ได้ join (ดีแล้ว), แต่ละ section ถือ Agent ID ของตัวเองอยู่แล้ว, ที่มี lookup ก็แค่ 1–2 collection ตอนทำ report; search หลักไปที่ BigQuery
- **Attribute Pattern** — สำหรับ field หลายตัวที่ทำหน้าที่คล้ายกันและต้อง search ทุกตัว (เช่น address 1–5, บัตรเครดิตหลายใบ) ให้ทำเป็น key/value (K/V) แล้ว index แค่ field เดียว — ประหยัด index แทนที่จะสร้าง index ทีละ field
- **Index management** —
  - MongoDB ไม่มี modify index ต้องสร้างใหม่แล้วลบเก่า
  - แนวทาง: สร้าง index ใหม่ก่อน แล้ว hide index เก่าไว้เป็น rollback plan (index ที่ hide ยัง update stat อยู่ กลับมาใช้ได้ทันที)
  - การสร้าง index ใช้ **hybrid build mode** (sync ช่วงแรกไม่กี่วินาที แล้ว rollback goal ทำแบบ parallel ตาม load) — ระบบยังทำงานได้ ไม่ block เหมือน MySQL ตอน migration
  - **ESR Rule** — สูตรออกแบบ index/query; ถ้าทีมเข้าใจ ESR จะสร้าง index ได้ถูกตั้งแต่แรก ไม่ต้องรอ Atlas advisor แนะนำสร้าง/ลบไปเรื่อยๆ (advisor จะแนะนำเมื่อ query ช้าเกิน ~100ms)

### ช่วงที่ 3 — CI/CD ของ Wallet (คุณเบ้น)

- **Pre-commit hook** — รัน Go test ใน local ก่อน commit ถ้า fail ให้ block ไม่ให้ commit (เขียนเป็น shell script). ข้อดี: รันด้วย resource เครื่องตัวเอง ไม่ต้องรอคิว pipeline
- **GitHub Actions ทางเลือก** — รัน test บน Action, ได้ Artifact/output, ใช้ Python format เป็น report ใส่ใน PR comment (แบ่งเป็น job Go test → job report)
- **Validate ENV/Secrets** — โจทย์: dev เพิ่ม ENV ใหม่ใน config.go แต่ลืมเพิ่มใน GitHub Secrets → deploy แล้ว pod cache ไม่ครบ. แนวทาง: ทำ job **Validate ENV** แยก (รันก่อน job test) อ่าน config.go/app config เทียบ key กับ Secrets ถ้ามีใน ENV แต่ไม่มีใน Secret ให้ stop + warning
- **ที่เก็บ Secret** — เทียบ Kubernetes Secret vs **GCP Secret Manager**:
  - GCP Secret Manager: มี audit log (ใครแก้อะไร), RBAC, กู้คืนได้, แยกจาก cluster → ปลอดภัยกว่า, เป็น one-time setup, ต่อ Uber/K8s ได้
  - ข้อควรระวัง: มีค่าใช้จ่าย (คิดต่อ operation) ถ้าเปลี่ยนบ่อยอาจต้องเช็คความคุ้ม
  - ถ้ามี cluster เดียว ใช้ Kubernetes Secret เดิมก็ยังโอเค
- ปัจจุบันต้นฉบับ ENV เก็บในเครื่องคุณเบ้นคนเดียว (พี่ฟี่แนะนำให้ย้ายไปที่กลาง)
