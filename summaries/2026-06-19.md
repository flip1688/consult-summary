## เนื้อหาสำคัญ

### 1. Architecture ของ OMBED (Thread — Wallet/Lotto)
- โครงสร้างมี 3 บทบาทเข้าระบบ: **agent / admin / payer** ผ่าน Gateway
- มีการต่อ API กับ **Game Provider** (ฝั่งค่ายเกม) โดยแยกเป็นหนึ่ง service ต่อหนึ่ง provider
- Service หลักมี **5 กลุ่ม**: User, Lottery Setting, Lottery Payment (Place), Report, และ Game Handler
- **Database:** ใช้ PostgreSQL ตัวเดียว แยกด้วย schema; Redis เป็น spec เดียว (ยังไม่แยก scale, ตั้งใจ vertical ก่อนแล้วค่อยแยกทีหลัง)
- **Timescale DB** = extension ของ PostgreSQL ใช้เก็บ transactions แบบ real-time ที่ Game Handler (ใช้ feature Hypertable, aggregate) — แนวคิด 1 database ต่อ 1 เกม อยู่บน server เดียวกับ Game Handler
- **การสร้าง user** จะถูก degrade ไป 2 ที่: ฝั่ง OMBED เอง และส่งไปสร้างที่ระบบภายนอก **Autofart** (Auto — ระบบ final ปลายทาง)
- **Message Queue** = RabbitMQ ใช้แบบ **Stream** (ไม่ใช่ Classic) มี 2 จุด: Game Handler เป็น producer (publish report), Report service เป็น consumer
- **Flow report:** Player เบ็ต → ผ่าน Gateway → Game Handler เปิด Game Provider → ตอนกดเบ็ตส่งกลับมา Handler สร้าง report → เก็บที่ตัวเอง (Timescale) แล้ว push MQ ไปให้ Report service; Report มี Worker ที่เปิด stream consume ตลอดเวลา (ไม่รอ trigger) เอายอดมา summary เก็บลง Postgres หลัก
- Handler มี API ให้ query ย้อนหลังได้เอง (safety ชั้น 2 กรณี MQ ล่ม/ข้อมูลไม่ตรง)
- **สถานะ:** develop ไปแล้ว ~80%, กำหนด launch เดือนหน้า (กรกฎาคม), ช่วงนี้เทสต์ API ให้ตรงกับ front-end
- ข้อสังเกตจากที่ปรึกษา: diagram ขาดทิศทางลูกศร (direction) และควรเพิ่มเส้นจาก Gateway → Timescale (เพราะ bet action มาจาก user จริง)

### 2. ปัญหา Scale ของ Lottery Service (LotPane — แทงหวย)
- service นี้แยกออกมาต่างหาก ใช้ **in-memory ของ Go เอง** (ไม่ใช่ memcache/redis) เพื่อความไวสูงสุด ทุกการเบ็ตเก็บใน memory ก่อนแล้วค่อย commit ลง DB ครั้งเดียวก่อน response
- ใช้ **optimistic concurrency**: เช็ค version ก่อน commit เข้า memory (เช็คเอง) — คนที่ 2 ที่ version ไม่ match จะเข้าไม่ได้
- โครงสร้าง agent: **Company (OMBED) → Agent → Sub-agent** ลงเป็นแนวดิ่ง (vertical/chain) **ได้สูงสุด 10 ชั้น** ไม่มีการแตกแนวข้าง; ล่างสุดคือ player/member
- แต่ละ agent ตั้ง **"เพดาน" (ค่ารับ)** ของตัวเอง เช่นเลข 3 ตัวบนรับไม่เกิน 1,000 บาท; เมื่อมีการเบ็ตยอดจะถูกหักลดลงเรื่อยๆ ทั้ง chain จนเหลือ 0 = รับไม่ได้ (ต้องตั้งใหม่ หรือมีเลขอื่นเบ็ตเข้ามาทบยอดให้)
- **ปัญหาหลัก:** ค่ากลาง/เพดานของ OMBED ตัวบนสุดต้องถูกใช้ร่วมกันโดยทุกคนแบบ real-time และหักลบทุก transaction — ทำให้ **scale แยกเครื่องไม่ได้** (ค่าอยู่ใน memory เครื่องเดียว) ทำได้แค่ upgrade spec
- ปัจจุบันช่วง peak (วันที่ 1–16 ก่อนหวยออก) ~1,000–2,000/วินาที, CPU ใช้ ~10–20%, เคย scale down จาก 16 core

### 3. ปัญหา Concurrency ของ Sports Betting (Thunder Software)
- **Flow เบ็ต:** เช็คสถานะแมตช์/คู่ (เปิดอยู่ไหม) → เช็คราคา (เปลี่ยนไหม) → สร้าง ticket (insert ได้ autonumber, ตรงนี้ไม่มีปัญหา) → ส่งหักเงินผ่าน Gateway → เช็ค KeyVed (ยอดสะสมต่อคู่/ราคา ห้ามเกิน) → commit
- **ปัญหา:** ลูกค้า 2 คนเบ็ตพร้อมกัน ดึง price ID เดียวกัน เช็ค max/min ได้ค่าเดียวกัน → คนที่ควรได้ราคาใหม่ (หลังคนแรกทำให้ราคาเปลี่ยน) กลับได้ราคาเดิม (race condition บนค่ากลาง)
- **ประเด็น Transaction scope:** step ที่ call Gateway (API ภายนอก) อยู่ใน `Begin Transaction` — ถ้า Gateway ช้าจะ hold memory/lock transaction นาน; MySQL transaction timeout อยู่ที่ 60 วินาที (rollback อัตโนมัติ), มี try/catch + เช็ค status ตอบกลับ, error → rollback
- **Gateway = Posted Wallet** เป็น function ที่ยิงไปหัก API ของลูกค้าแต่ละเจ้า (คนละ provider/ธนาคารกัน) → ควบคุมความเร็วไม่ได้ บางเจ้าช้า 30 วินาที+; แยกเบ็ตตาม provider ไม่ได้เพราะ wallet ผูกกับ player ราย ๆ
- ที่ผ่านมาถ้า Gateway fail = ปล่อยให้ fail (ลูกค้าเบ็ตใหม่) ยังไม่มีข้อกำหนด SLA/timeout ชัดเจน

## การตัดสินใจ / ข้อตกลง
- **Lottery scale:** เห็นพ้องแนวทาง — แยกส่วน "ค่ากลาง/เพดาน" ออกไปเป็น service/pod กลางแยกต่างหาก แล้วใช้แนวคิด **insert-based + queue + single consumer** (เหมือนเคาน์เตอร์ธนาคาร) แทนการ update/หน่วง lock; ยอมรับ latency เพิ่ม (อาจใช้ MQ) เพื่อแลกกับความสามารถในการ scale จำนวน agent; ทีมจะไปลอง prototype แยกดู speed
- **Sports concurrency:** เห็นพ้องใช้ **queue ด้วย insert** ลง temporary ticket table (MySQL หรือ Redis/cache) — แต่ละ record ได้ ID ลำดับ, ก่อนทำต้องเช็คสถานะ record ก่อนหน้า (done/reserved); **group by number** — คู่/เลขเดียวกันเข้าคิวรอกัน, คนละเลขทำ parallel ได้เลย; แนะนำทำบน memory/Redis (Key value) จะเร็วกว่า query DB
- **Transaction scope:** ยอมรับได้ที่ step หนักรวมใน transaction เดียว (auto rollback ทำงานถูก) แต่ต้องระวัง Gateway ช้าที่จะ hold นาน
- ที่ปรึกษาแนะนำเชิงธุรกิจ: ควรกำหนด SLA/timeout กับ Wallet provider หรือชี้นำลูกค้าให้ใช้ wallet ที่เร็ว/แนะนำ หรือแยก provider ที่ช้าออก เพื่อไม่ให้กระทบ platform ช่วง peak
- ยืนยันหัวข้อ Sports = **Security Review** (3 ประเด็นตามเอกสารเดิมที่ส่งไป), Wai Production = **รีวิว Git/Code** (รอ Infra เข้าร่วม)
