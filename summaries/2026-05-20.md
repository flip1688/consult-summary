- ข้อสรุปเรื่องกระบวนการ: ที่ปรึกษาจะทำ **High Level overview** ของแต่ละหัวข้อมาให้ก่อน แล้วค่อยแตกลงดีเทล/ทดลอง implement ทีหลัง และจะ **ตั้งหัวข้อของสัปดาห์หน้าล่วงหน้า** เพื่อให้ทั้งสองฝั่งเตรียมตัวได้

### 2. Application Security (โฟกัสหลักของรอบนี้)
กรอบ Security แบ่งเป็น 3 ส่วน: **Application / Infra / Database** โดยรอบนี้เน้น Application Security เพราะเชื่อมโยงกับปัญหาที่เจอจริงใน GitHub repository (Connection String / Secret ถูก expose)
- **Code Scan — SonarQube (Community Edition, ฟรี):** สแกนหา code smell / ช่องโหว่ตั้งแต่ตอน Development เพื่อไม่ต้องย้อนกลับมาแก้ทีหลัง ที่ปรึกษาแนะนำให้วางจังหวะสแกน **ตอน build เป็น image ก่อน deploy** (ทีม 1BX ใช้ Cloud Build ไม่ได้ใช้ GitHub Actions) รันเป็น Software/Container บน Cloud (deploy บน GKE/Cloud Run) provision ตัวเองเป็นเว็บเก็บ report/history ใช้ได้หลายโปรเจกต์ ที่ปรึกษาติดตั้งตัวตั้งต้นไว้แล้วแต่ยังไม่สมบูรณ์ (ยังไม่ผูก pattern scan ครบ) — ให้ทีมลอง deploy เองก่อนเป็น challenge
- **OWASP ZAP (E2E / DAST, ฟรี):** สแกนช่องโหว่ตามมาตรฐาน OWASP Top 10 แบบ Black Box หลัง deploy ขึ้น staging รันแบบ command line ใน Cloud Build ยิงไปที่ URL staging ออกเป็น report score (High/Medium/Low) เก็บไว้บน Cloud Storage/Drive ที่ปรึกษาทำ demo/simulate มาแล้ว
- **Burp Suite:** เวอร์ชัน Community (ฟรี) ไม่มี automation และไม่มี scan port; เวอร์ชันเสียเงินมีไว้เพื่อ **format report มาตรฐานขั้นสูง** สำหรับกรณีต้อง pitch/ให้บริษัทอื่นประเมิน — สรุปคือ **ยังไม่จำเป็นต้องซื้อ** ถ้าไม่มีใครต้องการ format report นั้น
- คำแนะนำเรื่องการลงทุน: ถ้าจะต้องเสียเงินจริง ๆ ควรลงทุนที่ **SonarQube** ก่อน เพราะปัญหาส่วนใหญ่เกิดจากฝั่ง Code/Development — แก้ที่ต้นทางคุ้มที่สุด

### 3. Infra Security
- 1BX ใช้ **Cloud Armor (WAF) + Armor Policy** อยู่แล้ว ที่ปรึกษาแนะนำให้ใช้เครื่องมือของ Cloud Provider (Google) ที่มีอยู่แล้วเป็นหลัก เพราะ Cloud Provider เป็น Security First และ patch CVE ให้ตลอด
- ปัจจุบัน **ยังไม่ได้เปิดฟีเจอร์ OWASP บน WAF** เพราะเปิดแล้วทุก request โดน reject (เป็นแอปเก่า)
- ประเด็นในการเลือกเปิดฟีเจอร์เพิ่ม: ต้องชั่งกับ **Response Time (สแกนทุก request แบบ real-time)** และ **Budget** — ที่ปรึกษาโน้มเอียงว่าไม่ต้องเปิด OWASP บน WAF ถ้าห่วงเรื่อง responsiveness เพราะ WAF ที่มีอยู่ก็ช่วยได้ระดับหนึ่งแล้ว
- คุณโดนัท/B ขอให้ที่ปรึกษาขยายความเพิ่มว่า Infra ต้องเช็ค/คอนเซิร์นอะไรบ้าง (Private, IP Whitelist ฯลฯ) — ที่ปรึกษาจะไปทำ detail มาให้ (ถ้า Infra มีอยู่แล้วก็ถือว่าพอ ถ้ายังไม่มีค่อยคุยว่าต้องเพิ่มเครื่องมืออะไร)

### 4. Database Security
- ใช้ **MongoDB Atlas** ซึ่งเป็น Security First อยู่แล้ว: Private Endpoint, RBAC (1 microservice = 1 user/role), Connection String ที่ secure
- Connection String / Secret ย้ายไปเก็บบน **GCP Secret Manager** เพื่อไม่ให้ค้างใน GitHub repository — ถือว่า work และครอบคลุม baseline แล้ว
- สรุป: DB Security ถ้ามี Private Endpoint + RBAC ถือว่าเพียงพอในระดับ baseline

### 5. Performance (หัวข้อของสัปดาห์หน้า)
- เครื่องมือ: ทีมใช้ **K6** อยู่ (มองว่า simple) ที่ปรึกษาเสนอ **JMeter** ที่ QA team นิยมใช้และให้รายละเอียด/กราฟมากกว่า — จะทำ overview + demo มาให้ (ที่ปรึกษาเคยใช้เมื่อ 6-7 ปีก่อน ต้องไปเช็คเวอร์ชันปัจจุบัน)
- โจทย์หลักจากคุณโดนัท: อยากรู้ว่า **ตัวเลข/metric ไหนที่ต้องดู** และ **อะไรคือมาตรฐานอุตสาหกรรม (จากประสบการณ์/connection ของพี่ฟี่)** สำหรับระบบเกม/เดิมพัน
- Context ตัวเลข (เป็น story ไม่ใช่ตัวเลขยืนยัน): เว็บมีคนเข้าราว 12,000-13,000/วัน, แทงพร้อมกันช่วงพีคราว 2,000-3,000; ปัจจุบัน backend อาจยังไม่ถึง 1,000 TPS; ผู้บริหารเทียบกับ AMB ที่อ้างว่ารัน 400,000 TPS
- แนวทางที่ปรึกษาเสนอ: เริ่มจากทำ **baseline** — วัด Database TPS/Response Time ตรง ๆ ก่อน (staging ปัจจุบันเป็น MongoDB M10, ยังไม่ได้ scale) แล้วค่อยไล่ทีละ layer; อาจขอข้อมูล/report เก่าจากทีมพี่แมน (เวอร์ชัน production เดิมที่มีลูกค้าใช้จริง เป็น MariaDB) มาใช้เป็น baseline เปรียบเทียบ

### 6. Database Design (หัวข้อเสริม)
- คุณโดนัทเสนอเพิ่มเรื่อง Database/Schema Design เพราะ cobbleneck ของ performance ส่วนใหญ่มาจาก query ช้า/schema ออกแบบไม่ match
- ที่ปรึกษารับว่าจำเป็นและจะช่วยรีวิว schema ของ 1BX (จะเปิด schema ให้ดูและจิ้มทีละ collection) แล้วสอนหลักการออกแบบเพื่อให้ระบบเร็วขึ้น — ทีมมี generate docs ด้วย AI อยู่แล้ว จะทำเป็นเอกสารส่งให้
- 1BX = แพลตฟอร์มเกม/เดิมพัน (มวย ฯลฯ) ที่ปรึกษาจะเทียบเคียงกับลูกค้ารายอื่นที่เคยออกแบบให้

- เปลี่ยนรูปแบบการประชุม: ทำ **High Level ก่อน แล้วค่อยลงดีเทล** และ **fix หัวข้อของสัปดาห์หน้าล่วงหน้า** ให้ทั้งสองฝั่งเตรียมตัว
- **Application Security baseline** = SonarQube (Community/ฟรี) + OWASP ZAP + (Secret Manager) ถือว่าเพียงพอสำหรับการเริ่มต้น
- **ยังไม่ซื้อ Burp Suite** จนกว่าจะมีความจำเป็นเรื่อง format report มาตรฐาน
- ถ้าต้องลงทุน Security ให้เน้นที่ **SonarQube (ฝั่ง Code)** ก่อน
- **Infra:** ใช้ Cloud Armor/WAF ที่มีอยู่ ไม่เปิด OWASP บน WAF (ห่วง response time/budget)
- **DB Security** baseline (Private Endpoint + RBAC + Secret Manager) ถือว่าผ่าน
- หัวข้อสัปดาห์หน้า = **Performance** เป็นหลัก (อาจเก็บตก Infra Security), ต้องการ **demo ทั้ง JMeter และ Database/Performance design**
