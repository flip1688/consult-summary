## เนื้อหาสำคัญ

### 1. เปรียบเทียบ PostgreSQL (Citus) vs MongoDB
- โดยรวม architecture คล้ายกันมาก ต่างกันที่ชื่อฟีเจอร์และ nature ของ DB
  - PostgreSQL = Relational, จุดแข็งคือ SQL, referential, ทำ replica ได้
  - MongoDB = Document, จุดแข็งคือ flexible schema, native BSON/JSON (Postgres รองรับ JSON แต่ไม่ native)
- ทั้งคู่ทำ sharding ได้ และ support ACID (MongoDB ตั้งแต่ v4.0), มี aggregation pipeline / SQL join — join เยอะก็เสีย performance ทั้งคู่, cross-shard query มี latency เหมือนกัน อยู่ที่การออกแบบ
- **Rebalancing:** Citus อาจต้องใช้ manual command; MongoDB Atlas เป็น auto-scaling / auto re-shard (scale up/down ได้)
- **ข้อกังวล Citus:** base อยู่บน Microsoft/Azure ต้องดูเรื่อง licensing ในอนาคต และต้องเช็คว่า Azure Managed (Citus) มี auto-scale จริงไหม (สับสนระหว่าง Flexible Server กับ Cosmos)
- **ตัวเลือก Cloud (จากคุณแซค):** GCP มี Cloud SQL for Postgres, AlloyDB (ระดับสูงขึ้น), Cloud Spanner (ระดับสูงสุด — ไม่ใช่ Postgres แต่มี interface ให้ใช้แบบ PostgreSQL ได้)
- **ประสบการณ์ที่ปรึกษา:** ลูกค้า high-end ต่างประเทศ (crypto/การเงิน/ธนาคาร/รัฐบาลนอกไทย, อเมริกา) ใช้ MongoDB เป็นระบบหลักรวมถึง online transaction จำนวนมาก → ทั้งสอง DB รองรับ transaction ได้ ขึ้นกับการออกแบบ schema
- **กรณี OpenAI:** ใช้ PostgreSQL ตัวเดียวแต่มี read replica เยอะ (~50) ไม่ทำ shard เน้นความเร็ว read/write; งาน analytics เดาว่าใช้ DB อื่นเสริม
- **Cloud support:** ทั้ง 3 cloud ติดต่อ support ยาก โดยเฉพาะ Azure/Microsoft ไม่มีตัวแทนในไทย ติดต่อผ่านออนไลน์อย่างเดียว → เป็นปัจจัยเสี่ยงเวลาเกิด incident กับระบบ shard ที่ซับซ้อน

### 2. เมื่อไรควรทำ Shard และการ Sizing
- เหตุผลหลักที่ทำ shard 3 ข้อ: (1) backup เร็วขึ้น (2) write/insert เร็วขึ้น (3) แบ่ง read ตาม zone/region
- **Rule of thumb:** collection/table เดียวโตเกิน ~500GB (ข้อมูลหลัง compression) ควรพิจารณา distribute; ฝั่ง Postgres อาจใช้เกณฑ์ต่างออกไป (อาจมากกว่า)
- RAM คือหัวใจของ DB — sizing ดูจาก RAM consumption; ไม่ควรปล่อยให้ RAM เหลือต่ำกว่า 10-20%, OS จะ OOM-kill process ที่ ~5%
- MongoDB by default จอง RAM ~50% (ปรับได้ 70-80%) และคืน memory กลับ ทำให้ไม่สวิงมาก
- ทำ shard เป็นราย collection/table ที่ size ใหญ่ก่อน ไม่ได้ทำทั้ง DB

### 3. Zone/Region Sharding + เลือก DB สำหรับ Analytics/Report
- ทำ zone shard โดยใส่ region เป็นส่วนหนึ่งของ shard key (เช่น user+region) → insert แล้ว distribute อัตโนมัติตาม region
- MongoDB Atlas ทำ Global Distributed วาง node คนละประเทศได้ (เช่น Singapore, จีน) — MongoS (query router) เช็ค region field แล้วส่งไป shard ที่ถูกต้อง (region-based / zone shard) มีคนใช้จริง
- คุณเบนสนใจใช้ MongoDB สำหรับฝั่งอ่านข้อมูล/รายงาน (analytics) — กำลังเทียบ **Tiger Cloud (TigerData)** กับ **MongoDB Atlas**
  - ปัจจุบันแยก DB: DB หลัก/user อยู่ GCP, DB report เป็น Tiger Cloud (บน AWS) — คร่อมระหว่าง GCP กับ AWS
- **เรื่องราคา:** แนะนำให้คุยกับคุณพงเรื่อง Commitment pricing (ถูกกว่า Pay-as-you-go หากใช้ต่อเนื่องระยะยาว)

### 4. รีวิว Use Case ระบบ Member/Wallet/หวย/Casino (คุณไอ)
- **ประเด็นหลัก — data consistency:** ให้ระบุให้ชัดว่า flow แต่ละเส้น select/return ข้อมูลอะไรออกมา (เช่น select ข้อมูล → return → กลายเป็น promotion/HTML) ลำดับข้อมูล (sequence) ต้องตรงกัน; แนะนำทำ dataset/data section ไว้ด้านบน
- แนะนำให้ทำเอกสารตามมาตรฐาน ISO (analysis) เป็น benefit และมาตรฐานให้ตักษอกของคุณไอ
- หน้าจอที่รีวิว: Landing/Category (กองเกมการ์ด), ค้นหา/Filter, อัตราจ่าย, กติกา, สมัครสมาชิก (2-step: เบอร์+รหัสผ่าน → สร้าง user/wallet ผ่าน service ไป AutoFast), เข้าสู่ระบบ, หน้าหวย, แทงหวย (คลาสสิก/จับวิน + โพย + จำนวนเงิน + ยืนยัน), ผลรางวัล, เลขที่ชอบ, Casino (ดึง API Game Provider), ประวัติเดิมพัน, ฝากเงิน (ผ่าน AutoFast, QR/บัญชี), ถอนเงิน, เพิ่มบัญชีธนาคาร, ประวัติฝากถอน, โปรไฟล์, โปรโมชั่น (จาก AutoFast), แนะนำเพื่อน (refer)
- **ข้อแนะนำสำคัญ:**
  - เพิ่มหน้ารายการ API / Table / schema แล้วทำ link จาก use case (เช่นกด Game Launch แล้วกระโดดไปหน้า API spec / Postman / OpenAPI Spec) เพื่อทำ PRD ให้ครบ ตรวจสอบ parameter กับทีม coding ได้ง่าย (design-first ก่อน coding)
  - Endpoint ด้านบนหน้าจอให้ทำ anchor/กระโดดได้ (กดจากด้านล่างเด้งขึ้นบน)
  - เคลียร์ชื่อ API: `Get API V1 Wallet Bank Account Deposit` ชื่อซ้ำกัน — เป็น API เดียวกันหรือคนละตัวระหว่าง OMBED กับ AutoFast? (คุณไอไปเช็คทีมหลังบ้าน) ถ้าคนละตัวให้ label เป็น AutoFast แทนคำว่า API
  - UC29 คำว่า "รอบปิดรับ/รับแทงแล้ว" กำกวม → เปลี่ยน keyword ให้ชัด เช่น "รอบหวยที่ปิดรับการเดิมพันแล้ว"
- **เครื่องมือ AI:** คุณไอใช้ Devin (เดิมชื่อ Windsurf แล้ว rebrand, เป็นตัวเสียเงิน) รีวิวทีละหน้า/ทีละ use case (ไม่สั่งทั้ง set เพราะ AI อาจทำบางอันตกหล่น) — พี่ฟี่แนะนำแนวคิด "skill" (สั่งครั้งเดียวแล้ว save เป็นชุดคำสั่งซ้ำได้/บันทึก record การแก้ต่อ use case/แชร์ให้ทีม เพื่อความ deterministic และลด error)

### 5. Data Migration ของ Wallet (คุณพาย) — MyGate / OMBED
- OMBED = โปรเจกต์ Wallet ใหม่ (โครงสร้างเดียวกับ Wallet ที่จะทำ MyGate)
- Wallet เก่า: **MySQL บน AWS RDS**; Wallet ใหม่ (OMBED): **PostgreSQL** — เดิมวางแผน Cloud SQL/GCP แต่อาจเปลี่ยนเป็น **AWS RDS PostgreSQL** เพราะ AutoFast อยู่บน AWS ใช้ private/VPC connection
- ต้องการวิธีย้าย MySQL → PostgreSQL และเครื่องมือที่ recommend
- **ข้อกังวลจากพี่แมน:** จะมี down time ไหม / ทำอย่างไรให้ไม่มี down time — ที่ปรึกษาพูดถึง AWS DMS (Data Migration Service); กังวลว่าระหว่าง migration แบบ continuous ระบบอาจช้า อาจต้องขยับสเปคเครื่องให้สูงขึ้นชั่วคราว
- คุณพายจะส่งโครงสร้าง Table ของ MySQL ตัวเก่าให้ที่ปรึกษาเช็ควิธีต่อ

## การตัดสินใจ / ข้อตกลง
- ทั้ง PostgreSQL และ MongoDB รองรับงานได้ทั้งคู่ (รวมถึง transaction) — เลือกจากความถนัดของทีม + การออกแบบ schema เป็นหลัก ไม่ใช่ที่ตัวฟีเจอร์; ถ้าถนัด Postgres และ shard ไม่ยากเกินไปก็ใช้ Postgres ต่อได้ ถ้าไม่ถนัดควรใช้ตัวที่มี auto-scaling/monitoring ง่าย (เช่น Mongo Atlas)
- คุณเบนจะเทียบ Tiger Cloud vs MongoDB Atlas (ราคา + ความเหมาะสมสำหรับ analytics) เอง
- คุณไอจะแก้ประเด็น consistency, ลิงก์ API/schema, และคำที่กำกวม แล้วอัปเดตความคืบหน้าผ่าน Telegram ให้พี่ฟี่รีวิวอีกครั้งสัปดาห์หน้า
- ทีม Sports (Thunder) สัปดาห์นี้ยังไม่ engage
- หัวข้อสัปดาห์หน้า: (1) Data Migration ของทีม Wallet (2) รีวิว use case ของคุณไอรอบใหม่
