# Meeting 2026-05-18

- **ทีมที่เกี่ยวข้อง:** ไม่ได้ระบุชื่อทีมตรงๆ ในบทสนทนา (ไม่มีการเอ่ยถึง OneBX/1BX, Wallet/Lotto หรือ Sports) — เป็น session เชิงกระบวนการ (process) ที่คุยกับ BA (คุณอาย) และอ้างถึง Tech Lead (พี่ลี่) โดยเนื้อหาเป็นมาตรฐานการทำงานที่ใช้ได้กับทุกทีม ตัวอย่างที่หยิบมาคุยคือหน้า Login (username/password/validate) ผ่าน ClickUp + Figma
- **หัวข้อหลัก:**
  - Flow เอกสารและ hand-off ระหว่าง BA -> ทีม Design / ทีม Backend
  - บทบาทของ BA กับ API Spec (OpenAPI/Swagger) และ Database Design เมื่อไม่มี System Analyst (SA)
  - การใช้ ClickUp เป็น single source of truth (Backlog, Test Case, Checklist)
  - Sign-off / หลักฐานการยืนยัน requirement ก่อนเริ่มเขียนโค้ด
  - พี่ฟี่จะจัดทำ list โครงสร้างเอกสารมาตรฐาน + ตัวอย่าง API Spec ให้

## เนื้อหาสำคัญ

### 1. Flow เอกสาร: BA ส่งงานให้ Design/Backend
- คำถามของ BA: หลังทำ SRS/PRD เสร็จ แล้วส่งให้ทีม Backend/Design ทั้งสองทีมต้องมีเอกสารส่งกลับมาไหม (เช่น Backend ส่ง API Spec กลับ)
- พี่ฟี่: ในทางปฏิบัติ **จะไม่มีเอกสารส่งกลับมา** — สิ่งที่ BA assign จะถูกทำลงไปใน repo ของทีมพัฒนา แต่ควรเพิ่มจุด "confirm/รับทราบ" ว่าเข้าใจตรงกัน (ผ่านเอกสาร/อีเมล/ระบบ digital)
- ทุกอย่างควร refer กับ ClickUp: Functional List จาก BA จะถูกแปลงเป็น Backlog ใน ClickUp; assign เสร็จ Tech Lead review/confirm แล้วทำงานร่วมกันได้เลย

### 2. บทบาท BA กับ API Spec (OpenAPI/Swagger)
- BA อยาก standardize API Spec ให้เป็นเหมือนบริษัทอื่นทั่วไป
- พี่ฟี่อธิบาย OpenAPI = standard กลาง (description เป็น markdown/YAML) ที่ทุกภาษาใช้ร่วมกันเพื่ออธิบาย spec; จะส่งลิงก์ Swagger + ทำตัวอย่างจาก function ที่เคยทำในรอบก่อนให้ดู
- BA "ควรจะรู้/เข้าใจ" API Spec แต่ไม่ต้องลงลึกถึงระดับโค้ด — หน้าที่คือ review ว่า spec ที่ dev สร้างล้อกับวัตถุประสงค์ของ function หรือไม่ (เช่น function เปลี่ยนสิทธิ์ทำครบ/ถูกต้องไหม) เพื่อกันปัญหา "ทำไม่ครบ" เพราะไม่มีคนตรวจซ้ำ

### 3. Database Design เมื่อไม่มี SA
- ทีมนี้ **ไม่มี System Analyst (SA)** — ตำแหน่งฝั่ง business ปัจจุบันมีแค่ BA กับ PM ไม่มี Solution Architect (พี่ฟี่ช่วยดูแลด้านนี้ให้)
- เมื่อไม่มี SA: BA กับ Tech Lead ต้องประชุมประสานกัน; Database Design เป็นงานของทีม Tech (Backend) โดย BA เข้าไปมีส่วนร่วม review ความครบถ้วน
- ปัจจุบันยังไม่มี Database Design แยกเป็น task ใน backlog (dev ทำโดยปริยายในงาน Backend) — พี่ฟี่แนะนำให้แยก UI / API / Database เป็น sub-backlog ภายใต้ Functional เพื่อให้ review แยกส่วนได้ และมี Change Schema ชัดเจนเมื่อ requirement เปลี่ยน
- พี่ฟี่ขอ perfect structure ขององค์กรซอฟต์แวร์ที่ควรมี (ตำแหน่ง/เอกสาร/งบประมาณ) และขอ org chart ตำแหน่งปัจจุบัน (ให้พี่ลี่ส่งให้) เพื่อประเมินว่า fit พอไหม แล้วปรับให้เป็น standard แบบ "average/พอเพียง" ไม่ over

### 4. Flow การทำงานจริงบน ClickUp (เดินตามตัวอย่างหน้า Login)
- Backlog 1 อัน (Functional/Non-Functional) ประกอบด้วย UI + API + Database — พี่ฟี่ยืนยันว่าโครงสร้างนี้ถูกต้องแล้ว
- Design: ทำ flow (เช่นหน้า Login มี username/password/validate) + Figma ที่ confirm แล้ว -> ให้ลูกค้า/ผู้บริหารดูก่อน -> มี feedback ก็แก้
- พี่ฟี่แนะนำให้ใส่ **Figma link ไปยัง wireframe หลัก** ในการ์ด (นอกจาก capture รูป) เพื่อกันกรณีรูปที่ copy มาผิด/ของจริงถูกเปลี่ยน และช่วย cross-check ได้ง่าย — BA รับไปทำ
- Backend: assign แยกเป็นอีก task/ตาราง; ควรมี Assign Link เชื่อม Backlog Frontend Login <-> Backlog API Login (project อื่นทำอยู่แล้ว แต่ตัวนี้ยังไม่สุด)

### 5. Test / Staging / Deploy
- หลัง dev เสร็จเข้า Staging -> BA/ทีมเปิดงานเข้าไปทดสอบ ปรับสถานะ Pass/Reject ใน ClickUp; ทีมทดสอบคือ BA + CS (Customer Service รับเคสแก้ไข)
- ปัจจุบัน **ยังไม่มีจุดระบุว่า test case ไหนผูกกับ function ไหน** — BA ต้องเทียบเอากับหน้า Frontend เอง
- พี่ฟี่แนะนำ (เป็น light comment): ใช้ ClickUp Checklist ใส่ Test Number + attach Test Case file/Google Sheet link + ติ๊กเมื่อผ่าน เพื่อให้การ์ดเดียวมีครบ (UI/API/DB/Test/คนทำ) ดูจบในที่เดียว
- เสร็จแล้ว Deploy และแจ้งลูกค้า
- ปัจจุบัน**ยังไม่มี link จาก ClickUp ไป repo (และจาก repo กลับมา ClickUp ก็ยังไม่มี)** — พี่ฟี่ตั้งข้อสังเกตว่าควรมี traceability

### 6. Sign-off / หลักฐาน requirement (ประเด็นสำคัญ)
- พี่ฟี่ชี้ช่องโหว่: ปัจจุบัน**ไม่มีหลักฐาน/จุด sign-off** ว่าผู้บริหาร/ลูกค้า OK กับ function จริงๆ ก่อนเริ่มเขียนโค้ด — เคยเกิดเคสข้ามขั้น design ไปลงโค้ดเลยแล้วไม่ตรง ("วันก่อนไม่ได้คุยแบบนี้")
- ต้องมี process sign-off requirement ระหว่างลูกค้า/เจ้าของ requirement กับ BA ก่อนเริ่ม coding เพื่อใช้อ้างอิงเวลาลูกค้าขอเปลี่ยน (จะได้คิดเงิน/เวลาเพิ่มได้)

## การตัดสินใจ / ข้อตกลง
- ยึด **ClickUp เป็น single source of truth**: Backlog = Functional/Non-Functional ประกอบด้วย UI/API/Database และควรแยก sub-backlog ให้ review ได้
- โครงสร้าง Backlog ที่ทีมทำอยู่ **ถูกต้องแล้ว** พี่ฟี่ยืนยัน
- BA มีบทบาทเข้าไปร่วม review API Spec และ Database Design (เพราะไม่มี SA) แต่ไม่ต้องลงลึกระดับโค้ด
- ต้องเพิ่มขั้น **sign-off requirement** ก่อนเริ่ม coding เป็นหลักฐาน
- Confirm/รับทราบระหว่างทีมทำผ่านระบบ digital ง่ายๆ (ไม่ต้องส่งเอกสารกลับ)
