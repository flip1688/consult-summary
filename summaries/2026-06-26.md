## เนื้อหาสำคัญ

### 1. ทีม Sports — วิเคราะห์ Performance / Capacity

- **ข้อมูล peak:** ผู้ใช้ออนไลน์สูงสุด ~6,100 คน (ช่วง 5 ทุ่ม 23 ของวันที่ 20–21) มากกว่าข้อมูลชุดก่อนราว 10%. API server มี 5 เครื่อง
- **ความไม่สอดคล้องที่พบ:** ตอนคน peak จริง (5 ทุ่ม) เครื่อง SportBook Daemon (ทำ payout/คำนวณผล) ใช้ CPU แค่ ~40% แต่ช่วงเที่ยงกลับพุ่งเกือบ 100% (ขึ้นแบบ spike แล้วลงทันที). สาเหตุคาดว่าเป็นการรวมบิลคำนวณผลตอนคู่ใหญ่จบ ไม่ใช่จำนวนผู้ใช้ — พี่ฟี่ขอให้เก็บสถิติว่า "รวมกี่บิลถึงทำให้ CPU พุ่ง" และ "ตอนนั้นมีผู้ใช้เท่าไร" เพื่อประเมิน limitation
- **ตัวที่เป็นคอขวด (Critical):** Feed Server / Pipe Feed — ช่วง peak ตัว Daemon ดึง Event Match ใช้ CPU ถึง 71% (สูงสุด). ถ้า scale ผู้ใช้เป็น 2 เท่าจะไปแตะ ~140% ซึ่งรับไม่ไหว. สเปกเครื่องที่น่ากังวลคือ M5 2XL (8 vCPU / 32GB RAM) ส่วนเครื่อง 8XL (128GB) ยังพอไหว
- **ฐานข้อมูล:** peak DB ต่ำมากเทียบกับจำนวนผู้ใช้ เพราะทำ caching (lookup) เยอะ. DB โดนหนักช่วง 10–11 โมง จากการปิด/เปิดคู่ (เปลี่ยนวัน) โดยผู้ให้บริการ (BTi) เป็นคนกำหนดเวลา เกิดเป็น pattern ทุกวัน
- **การวิเคราะห์บิลที่ช้า:** บิลรวมทั้งหมด ~120,000–130,000 บิล/วัน. บิลที่ช้าเกิน 1.5 วิ มี ~370 บิล (~25% ของแต่ละสาย). ช้าสุด ~26–30 วินาที ค่าเฉลี่ยรวม ~0.5 วิ. ความช้าอยู่ที่ Gateway (ตอนยิงจ่ายเงินให้ลูกค้า) ไม่ใช่ logic. ยังไม่มี feedback เชิงลบจากลูกค้า
- **ข้อสังเกตด้านต้นทุน:** จ่ายค่า infra ~1 ล้านบาท/เดือน รองรับ ~6,000 คน. โจทย์คือหา limitation ของระบบ (6k → 8k คนไหวไหม) ก่อนตัดสินใจ scale หรือลดต้นทุน

### 2. ทีม OMBED — Grafana / Observability (นำเสนอโดยพี่ฟี่)

- ปัจจุบันลูกค้าใช้ LGTM stack. แนะนำเครื่องมือใหม่จาก GrafanaCon: เวอร์ชันใหม่ (13.1) ใส่ AI เข้ามามากขึ้น
  - **Alloy:** collector สำหรับส่งข้อมูล (แทน agent เดิม)
  - **Beyla (ในทรานสคริปต์เขียนเพี้ยนเป็น "Bella"):** ใช้ eBPF ระดับ kernel ดึง trace/metric อัตโนมัติ **โดยไม่ต้องแก้โค้ด** (ไม่ต้องฝัง OpenTelemetry SDK เอง) — พี่ฟี่ย้ำว่าต้องทดลองจริงว่าดึง custom metric ได้แค่ไหน อาจได้แค่ metric พื้นฐาน
  - **Pyroscope:** profiler ดู CPU/RAM ละเอียดระดับ application performance
  - **Grafana Assistant:** AI ถามตอบ/query data ได้ (คล้าย ChatGPT ข้าง dashboard) — ข้อมูลจะถูก sync ขึ้น Grafana Cloud Free Tier (มี token limit/เดือน) ไม่เก็บถาวรที่ On-Prem
  - **OpenCost:** monitor ค่าใช้จ่าย cloud, breakdown ราคาต่อ resource ได้ละเอียด (รวมหลาย cloud/หลาย project ได้ถ้าจัด group ผ่าน IAM)
  - Loki/Tempo/Mimir มุ่งใช้ OpenTelemetry เป็นมาตรฐาน, เก็บ log ที่ GCS/S3 เพื่อประหยัด storage
- **ข้อเสนอ:** รวม view ของ database (ที่ปัจจุบันดูแยกผ่าน pgAdmin/tool อื่น) เข้ามาใน Grafana เป็น All-in-One โดยสร้าง Grafana User + Report View แยก layer จาก Database User เดิม เพื่อบริหารจัดการง่ายขึ้น

### 3. ทีม OMBED — การจัดการข้อมูลปริมาณมาก (TimescaleDB)

- ระบบใช้ PostgreSQL + TimescaleDB. ออกแบบใช้ **HyperTable** เก็บ slot ticket โดยตั้ง compression policy (บีบอัดข้อมูลเก่าเกิน 30 วัน) และเลือก move ไปอีก node/database ได้
- **สถาปัตยกรรม 3 tier ที่พี่ฟี่อธิบาย:** Hot (ล่าสุด) → Warm (บีบอัด อยู่ใน table เดิม ใช้ time เป็น key) → Cold/Archive (แนะนำย้ายออกไป S3, PostgreSQL fetch มาได้แต่ช้าลง)
- **ประเด็นที่ต้องพิจารณา:**
  - Warm ที่บีบอัดต้องกำหนด segment/order key ตั้งแต่แรก (แก้/เพิ่มได้ภายหลัง), query ได้ทั้งข้อมูลที่บีบและไม่บีบใน table เดียว
  - ต้องประเมิน: query warm บ่อยแค่ไหน, side effect ของ index (ถ้า index ยังโตเรื่อยๆ size ของ slot ticket ก็ยังโตอยู่ดี), ความ complex ของการ manage chunk, และ limitation (เช่นถึงกี่ TB จะเริ่มช้า)
  - พี่ฟี่แนะเปรียบเทียบกับสไตล์ Mongo (แยก archive ชัดเจน): ถ้าไม่ได้ query warm บ่อย การ**แยกออกไปเลย**อาจดีกว่า เพื่อไม่ให้ slot ticket (ตารางที่ใช้งานประจำ) รับภาระ
  - ระยะยาว ถ้าจะ move จริงให้ใช้ `set_node` + distributed hypertable กระจายไปอีก node

### 4. ทีม OMBED — Race Condition ของ Wallet รวม

- **ปัญหา:** ทุกโปรดักต์ (หวย, สลอต ฯลฯ) ใช้กระเป๋าเงินใบเดียวกัน. เมื่อหวยคิดผล/จ่ายเงิน (update balance) ตรงกับจังหวะที่ผู้ใช้เดิมพันสลอตพร้อมกัน เกิด transaction ชนกัน → เสี่ยง deadlock/ข้อมูลทับกัน
- **วิธีปัจจุบัน:** lock row (queue รอทีละ transaction) — ยอมรับได้ แต่กังวลว่าช้าและหน่วง API อื่น (ยังอยู่เฟส dev ยังไม่ test จริง)
- **แนวทางที่พี่ฟี่เสนอ:**
  1. **ทำ operation เดียวจบใน UPDATE เดียว** (atomic): `UPDATE wallet SET amount = amount + X WHERE wallet_id = ? AND amount = <ค่าเดิม>` — lock เฉพาะจังหวะ update ไม่ต้อง lock ตั้งแต่ validate. การใส่เงื่อนไข `amount = ค่าเดิม` การันตีว่าถ้า 2 transaction เข้าพร้อมกันจะมีแค่คนเดียวสำเร็จ อีกคน fail → **retry** (select ค่าใหม่แล้วทำซ้ำ). ต้องกำหนดจำนวนรอบ retry ก่อนแจ้งลูกค้าให้ลองใหม่
  2. **ทำเป็น Queue** (คนมาก่อนได้ก่อน แล้ว consume ทีละรายการ) — เหมาะกรณี traffic รัวมาก แต่ต้อง provision เครื่องเพิ่มและลูกค้าต้องรอผล ไม่เห็นยอดทันที
- คีย์คือ: ถ้าลูกค้าต้องเห็นยอดทันที ใช้ท่า atomic update; ต้อง lock เฉพาะ single operation เท่านั้น อย่ารวมหลาย step ในสิ่งที่ถูก lock

### 5. ภาพรวม — Company Knowledge Base + AI Agent

- พี่ฟี่ชวนคิดว่าธุรกิจนี้มี use case ไหนใช้ AI agent แทนคน/ช่วยตอบ incident ได้ (มุม Player และมุม Operator เจ้าของเว็บ) เช่นทำ Knowledge Base ถามตอบข้อมูลลูกค้า
- ปัญหาที่ยกขึ้น: knowledge กระจัดกระจาย (Notion / ClickUp / MD ในเครื่องตัวเอง) ไม่มี knowledge base กลาง และแต่ละคนใช้ AI ต่างระดับกัน
- พี่ฟี่เล่า pattern ของ MongoDB (องค์กร ~6,000 คน): ทุกอย่างที่ contribute ให้ลูกค้าเก็บใน Google Drive → ถูก index อัตโนมัติ (คล้าย NotebookLM / "LLM Anything") → search เจอทั้งหมด รวมถึง email/GitHub บริษัท (เป็น policy). ข้อมูลส่วนตัวห้ามใส่. Slack ไม่ index (กลัวเป็น noise). ใช้ Enterprise Search ที่ตอบเฉพาะเรื่องในองค์กร ออกนอกเรื่องไม่ได้ — ผู้ใช้ต้อง validate เอง
- **ความเสี่ยงด้านความปลอดภัย:** ถ้ารวม knowledge กลางแล้วถูก hack จะเสี่ยงมาก → หัวใจอยู่ที่ Authentication (MFA / authenticator app), การจัดการสิทธิ์, และการให้ความรู้พนักงานให้ใช้เครื่องที่ปลอดภัย/เหมาะกับงาน

- **Sports:** ระบบปัจจุบันยังไม่มีปัญหาเชิง performance ที่ลูกค้ารับรู้ ต้นทุน/CPU ยังรับได้ — เห็นชอบให้เดินหน้าทำ load test เพื่อหา limitation ก่อน แล้วค่อยตัดสินใจเรื่อง scale/optimize (สองโจทย์ "รองรับผู้ใช้เพิ่ม" กับ "ลดต้นทุน" ขัดกัน ต้องเลือกน้ำหนักก่อน)
