## เนื้อหาสำคัญ

### กลุ่มผลิตภัณฑ์ (Product Group) — การตั้งค่าแบ่งหุ้น/ถือหุ้น ของเกมคาสิโนและหวย
- หน้ารายการกลุ่มผลิตภัณฑ์เป็นหน้ากลาง (แสดงชื่อกลุ่ม + จำนวนสมาชิกในกลุ่ม) กด action ไปหน้าอื่นต่อ
- แนวคิดเปลี่ยนจากเดิม "1 user 1 การตั้งค่า" มาเป็น "1 กลุ่ม หลาย user" — กลุ่มคือกลุ่มของสมาชิก/เอเจนต์ที่ตั้งค่าเหมือนกัน
- Workflow: สร้างกลุ่มก่อน (เช่น กลุ่มเน้นคาสิโน/เน้นหวย/เน้นเกม) แล้วเวลาเพิ่มสมาชิกจึงเลือกกลุ่มได้ (1 คน = 1 กลุ่ม แต่แก้ไข/ย้ายได้)
- ชื่อกลุ่มห้ามซ้ำ **เฉพาะภายใต้ Agent เดียวกัน** เท่านั้น (ไม่ใช่ทั้งระบบ) — คนละ Agent ตั้งชื่อกลุ่มซ้ำกันได้
- เพิ่ม/แก้ไข/ลบกลุ่ม เขียนเป็น API ตรงไปตรงมา. ลบกลุ่มได้ต่อเมื่อไม่มีสมาชิกอยู่ในกลุ่ม (ต้องย้ายคนออกก่อน)
- การย้ายกลุ่มทำที่หน้า "แก้ไขรายชื่อสมาชิก"; ระบบไม่ล็อก แต่ในทางปฏิบัติต้องแจ้ง/คุยกับสมาชิกก่อนย้าย เพราะกลุ่มเกี่ยวข้องกับผลประโยชน์/เงิน (ค่าคอมมิชชั่น)
- **ข้อเสนอ (nice to have อนาคต):** ที่ปรึกษาเสนอกลไกความปลอดภัยแทนการ "คุยด้วยปากเปล่า" — เช่นเวลาจะปิด/ย้ายกลุ่มให้มี status lock/release ใน DB, ส่ง request ให้อีกฝ่าย confirm (ผ่านอีเมล/Telegram) กัน error จากการโยกกลุ่มโดยพลการ

### รายการผู้ช่วย (Assistant) — UC8–UC12
- ผู้ช่วยเป็นลูกมือของ Agent (Agent มีผู้ช่วยได้ไม่จำกัดจำนวน) สิทธิ์กำหนดจาก Role ที่ backend ตั้งไว้ (เช่น ทีมบัญชีดูได้แค่ Report, ผู้ช่วยระดับใกล้ Agent แก้รายชื่อสมาชิก/แก้กลุ่มได้)
- ผู้ช่วย ≠ สมาชิก: ผู้ช่วยเล่นเกมไม่ได้/ไม่รับเงิน ทำได้แค่งานตาม role; สมาชิกใต้ Agent = ผู้เล่น (member)
- UC ผู้ช่วยต้องเชื่อมกับ AutoFast ด้วย (มี UC จัดการสิทธิ์ผู้ช่วยว่าใช้หน้าไหนของ AutoFast ได้บ้าง) — จึงต้องแก้ flow เพิ่ม
- UC12 (แก้ไขผู้ช่วย) ผู้นำเสนอขอติดไว้ก่อน ยังไม่มั่นใจเรื่องเส้น flow

### โครงสร้างลำดับชั้น Agent (สำคัญต่อความเข้าใจทั้งระบบ)
- ลำดับชั้น: Company (บนสุด) > Master > Senior > Super > Agent > Member
- แต่ละระดับสร้างสมาชิกระดับต่ำกว่าตัวเองได้; สมาชิกที่อยู่ใต้ Agent โดยตรง = ผู้เล่น (Member) จริง
- ระดับที่สูงกว่า Agent ทำหน้าที่รับส่วนแบ่งคอมมิชชั่น ไม่ได้เล่นเกมเอง

### กลไกถือหุ้น/แบ่งหุ้น หวย (share / อัตราจ่าย) — ส่วนที่ซับซ้อนที่สุด (พี่ปออธิบาย)
- แต่ละ Agent สร้าง "กลุ่มถือหุ้น" ของตัวเองก่อนจึงจะสร้างสมาชิกระดับถัดไปได้ และระบุให้สมาชิกใช้กลุ่มนั้น (ไล่ลงเป็นชั้น ๆ เช่น X → X1 → X11 → member)
- "ถือหุ้น" = สัดส่วนที่แต่ละคนรับไว้เอง vs "ให้" = สัดส่วนที่ส่งต่อลงชั้นล่าง; รวมกันในแต่ละสาย **ห้ามเกิน 100%** (ขาดได้ แต่เกินไม่ได้)
- เมื่อ member แทงเข้ามา ยอดจะถูกคำนวณแบ่งตามสัดส่วนการถือหุ้นของทุกระดับ และเพดานรับของแต่ละคนถูกหักลดอัตโนมัติแบบ real-time
- อัตราจ่าย (payout) เป็น preset จากบริษัท (เช่น 3 ตัวบน จ่ายจาก 900–1,200 ต่อ 1,000, สูงสุดราว 12,000 สำหรับ 4 ตัวบน); Agent แต่ละคนปรับได้เฉพาะ % การรับ ปรับเพดานจ่ายเกิน preset ไม่ได้
- คนตั้งเลข/แก้เลขให้ Agent คือระดับที่สูงกว่า 1 ชั้น (เช่น Master ตั้งให้ Agent). Member/ผู้เล่นไม่เห็นหน้าตั้งค่าเหล่านี้
- พฤติกรรมจริง: Agent ปรับเลขถี่ช่วง ~3-4 ชม.ก่อนหวยออก และตอนเปิดงวด (สร้างรอบหวย) — เป็นระบบ Dynamic ข้อมูลเยอะ

### ประเด็นเทคนิค / สถาปัตยกรรม
- ใช้ in-memory cache เก็บยอด/เพดานต่อ (key = ประเภทหวย+งวด+เลข, value = ยอด + user id ของแต่ละลำดับเอเจนต์) พร้อม **version** กัน concurrent update ทับกัน (บวก 1 ทุกครั้งที่แทง, ต้อง version ตรงจึงเขียนได้)
- ปัจจุบัน memory อยู่ใน Go process เอง (เขียน mem table ใน Go + console) ไม่ได้แยก Redis; node ปัจจุบัน 2 CPU ใช้ทรัพยากรยังเหลือเยอะ
- ข้อมูลหน้า Agent (คาดคะเนได้เสีย ฯลฯ) ดึงแบบ **Polling API ทุก ~30 วินาที** ผ่าน memory cache; ยังไม่ใช้ WebSocket
- ถกทางเลือก scale: Redis + sharding, การทำ shard บน MongoDB vs Postgres (extension **Citus**); WebSocket ให้ความเร็ว/up-to-date แต่กิน spec/network มาก (ต้องเปิด connection ค้าง) — ยังไม่สรุป
- หน้าอื่น ๆ ที่รีวิว: ค่าคะเนได้เสีย (report real-time), กลุ่มตั้งสู้, ตั้งค่าปิดบิลหวย, assign อัตราจ่ายให้หวยแต่ละประเภท, รายงานแพ้ชนะ/รายงานดูของ, รายงานยกเลิก, สร้าง/แก้รอบหวย, จัดการผลรางวัล, กติกาหวย (แสดงให้ลูกค้าดูเฉย ๆ ไม่ได้คำนวณผล), ปิด/เปิดผลิตภัณฑ์ (maintenance ค่ายเกม เช่น PG), รายงานเกมคาสิโน, จัดการค่าเกม, ประกาศ, activity log, ชำระค่าบริการ (บิล API/AutoFast รายเดือน), คู่มือ, ติดต่อเจ้าหน้าที่
